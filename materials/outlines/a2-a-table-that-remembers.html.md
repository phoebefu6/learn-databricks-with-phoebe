# a2-a-table-that-remembers.html · "Leader session 2 of 6" · Delta: a table that remembers

Win: a one-page retention policy for one important table (how far back time travel must reach, who may VACUUM, who may RESTORE), and the sentence "every change is a numbered commit, and history lasts exactly as long as we decide."

Part 1 · covers the log as a numbered list of commits · "Every change is a numbered commit" · 5 min live
- Figure (prefix a2a): the bench table's real history as a vertical ledger: v0..v30 one append per day (31 files), v31 MERGE (1 remove, 1 add, 1 cdc), v32 DELETE of 113 voided trips (30 files removed, 8 added), v33 OPTIMIZE (dataChange false), v35 RESTORE (dataChange true, on the vendor branch). Mechanism: a commit adds and removes whole files; nothing is edited in place.
- Cards: (open, Live) "Versions are commits" - each write adds one JSON file named by its zero-padded version; a reader at version N sees exactly the files live after commit N (PROTOCOL.md). (Live) "History is an audit trail" - DESCRIBE HISTORY returns one row per commit with operation and parameters; the Delta paper shows DESCRIBE HISTORY "showing where each update came from". (Self) "What a commit costs" - a 113-row DELETE rewrote 30 of 31 files on the bench; deletes and updates are file rewrites (copy-on-write), which is why they are not free.
- Real world: the voided-trip DELETE on the bench (real numbers above) as the story of an auditor asking "what did the table say before the cleanup?".

Part 2 · covers time travel and RESTORE · "Asking the table about last Tuesday" · 5 min live
- Figure (a2b): time travel mechanism: a slider over versions, three readers at v0, v31 and v33 each pointing at a different set of files on the same storage; RESTORE drawn as a NEW commit that re-adds old files (v35 restores v33's 8 files), not as rewinding the log.
- Cards: (Live) syntax a leader should recognise: `VERSION AS OF 123`, `TIMESTAMP AS OF '...'`, `@v123` (Databricks docs). (Live) RESTORE is "a data-changing operation" with dataChange true, so streaming consumers may reprocess restored data as duplicates (docs) - a governance point: restoring is a change that downstream sees. (Self) the analyst numbers: on the session-3 laptop table, VERSION AS OF 0, 1, 2 return 21,617, 77,033 and 76,103 rows; RESTORE to 1 creates version 3 with 77,033.

Part 3 · covers retention and VACUUM · "History lasts as long as you decide" · 5 min live
- Figure (a2c): a timeline with two clocks: log retention `delta.logRetentionDuration` default 30 days (history entries) and file retention `delta.deletedFileRetentionDuration` default 7 days (removed data files VACUUM may delete); VACUUM cuts time travel at the file retention line. Mark the gap: history may still list a version whose files are gone.
- Cards: (Live) defaults 30 days / 7 days, both table properties (docs); VACUUM default retention 7 days; "If you run VACUUM on a Delta table, you lose the ability to time travel back to a version older than the specified data retention period." (Live) the safety check `spark.databricks.delta.retentionDurationCheck.enabled` blocks risky VACUUMs; DRY RUN lists up to 1,000 files; LITE vs FULL. (Self) what happened when the analyst track forced retention to zero: 1 file deleted, time travel to version 2 failed with FileNotFoundError, latest still read 77,033 rows. Retention is a cost-versus-recoverability trade: longer retention keeps more removed files in storage.
- Real world (constructed, say so): a finance team that needed month-end figures as they were reported, and a VACUUM schedule set by an engineer with retention 0 to save storage.

Build-along (no code): "Write the retention policy for one table" · figure (a2d): a one-page policy card with fields (table, why history matters, time-travel window, file retention, log retention, who may VACUUM, who may RESTORE, who is told) and one constructed example row filled.
Steps: pick the table an auditor would ask about; decide the window in days and justify it; set the two properties (prompt-box with `ALTER TABLE your_catalog.your_schema.orders SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 30 days', 'delta.logRetentionDuration' = 'interval 90 days')` labelled as the statement an engineer would run, not run in this build); name who may run VACUUM and RESTORE and who must be told; write the "history we promise" sentence. Bad box: "VACUUM nightly with RETAIN 0 HOURS to save storage". Tip: retention is a promise to auditors and to downstream readers; write it down where they can find it.
Quiz: (1) what a version is (a commit that adds/removes whole files); (2) VACUUM after retention means time travel to older versions fails (not "history is rewritten"); (3) RESTORE is a new commit with dataChange true, so streaming consumers may see duplicates.
Covered: PROTOCOL.md (commits, versions, tombstones) read at source; Databricks docs "Work with table history" and "VACUUM" read at source; bench and laptop numbers measured; finance story constructed (◐).
Cheat: one commit = one version; files never edited; VERSION AS OF / TIMESTAMP AS OF / @v; 30-day log, 7-day files; VACUUM ends time travel past retention; RESTORE is a new commit.
