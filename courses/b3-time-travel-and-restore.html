Part 1 · covers time travel

Time travel is the replay, stopped early

5 min live

Reading "version 1" does not mean finding an old copy of the table. There is no old copy. The reader replays the log from the start and stops after commit 1, and whatever files are live at that point are the table as it was. Because Delta never edits or deletes a data file when it commits, the files every earlier version needs are still sitting in the folder.

LiveAsking for a version, on the laptop and in Databricks2 min▶

In delta-rs you pass the version when you open the table: DeltaTable("trips_delta", version=1). Tonight's run printed 21,617 rows for version 0, 77,033 for version 1 and 76,103 for version 2, the same counts session 2's hand replay produced.

In Databricks the Databricks documentation page on table history gives three spellings in SQL: SELECT * FROM t VERSION AS OF 1, SELECT * FROM t TIMESTAMP AS OF '...', and the shorthand t@v1 after the table name. All three are the same operation: pick a version, replay to it, read its files.

LiveHistory: the log, read newest first2 min▶

DeltaTable.history() in delta-rs and DESCRIBE HISTORY in Databricks both return one row per commit, newest first. Tonight's table prints 2 DELETE with its predicate fare_amount < 0, then 1 WRITE with mode Append, then 0 WRITE with mode ErrorIfExists, the default "create, or fail if it exists" mode from session 1. Each row is the commitInfo action you read in session 2, so history is an audit trail you get for free: who changed what, when, and with what condition.

Read history before you time travel or restore. It is the only way to know which version number you actually want.

Self-studyTimestamps, checkpoints and how far back a reader may start2 min▶

Travelling by timestamp needs a reliable time for each commit. The protocol defines an In-Commit Timestamps table feature that writes the commit time inside the commit itself; this session only names it, because tonight's table travels by version number.

Session 2 wrote a checkpoint at version 2. PROTOCOL.md says that "For time travel, the checkpoint used must not be newer than the time travel version", so a reader asked for version 0 or 1 cannot start from that checkpoint and replays the JSON entries from version 0 instead. The checkpoint is a shortcut to the present, never to the past.

Real world

Files change, answers do not. Open the Delta log bench (analyst session 8), choose the JFK preset and drag the version slider. At v30 the JFK question finds 371 rows in 31 daily files. Then come a MERGE (v31) and a DELETE of 113 voided trips (v32), real data changes, so the count moves. At v33 OPTIMIZE rewrites the live files into 8 with dataChange false, and the answer is 358 rows; the bench's RESTORE back to v33 at v35 answers 358 again from the same 8 files. Time travel follows the log, not the folder, so a layout change never alters what a version contains. These are run numbers from the bench's own build.

Part 2 · covers RESTORE

Undo is a new commit

5 min live

The log rule from session 2 still holds: writers never overwrite or delete an existing log entry. So RESTORE cannot rewind the table by erasing commits. It works out the difference between the version you want and the version you have, and writes one new commit that removes and adds files until the live set matches. Version 2 stays in the history, exactly as it happened.

LiveWhat tonight's RESTORE printed2 min▶

dt.restore(1) followed by a fresh read printed after RESTORE: version 3 rows 77033. Two facts in one line: the row count is back to version 1's 77,033, and the version number went up, to 3, not back to 1. If you run history now, it lists four commits with RESTORE on top.

In Databricks the same move is RESTORE TABLE t TO VERSION AS OF 1, or TO TIMESTAMP AS OF a point in time.

LiveWhy "data-changing" matters downstream2 min▶

The Databricks history documentation calls RESTORE "a data-changing operation": its commit marks the files it adds and removes with dataChange true, unlike session 2's checkpoint or an OPTIMIZE. Anything that follows the table commit by commit, such as a streaming job, treats the re-added files as new data and may process those rows a second time. The table is right after a RESTORE; a copy built from its changes can hold duplicates. How streaming readers handle that is the subject of the streaming data course; on the Delta side, the rule is to check who reads the table incrementally before you restore it.

Self-studyThe same commit at bench scale2 min▶

The bench restores its vendor branch from v34 back to v33. The v35 commit delta-rs wrote holds a protocol action, a metaData action, 8 remove actions and 8 add actions, with dataChange true, and the live set afterwards is the same 8 files v33 had. Notice that v34 was an OPTIMIZE with dataChange false, yet undoing it is a data-changing commit: RESTORE does not inherit the flag of the change it reverses.

Real world

The Friday DELETE and the Monday double count. An analyst runs a DELETE with a predicate that is too wide on Friday. On Monday a colleague spots it in DESCRIBE HISTORY, finds the version before it, and runs RESTORE. The table is correct within seconds. But a streaming job copies every change from that table into a reporting table, and it now sees the restored files as new rows, so the reporting table counts the same trips twice until someone rebuilds it. This team is constructed; the mechanism is the documented one, and it is why a restore deserves a message to every downstream owner.

Part 3 · covers VACUUM and retention

The command that ends history

5 min live

Time travel and RESTORE work because removed files stay on disk as tombstones. That costs storage, so Delta gives you VACUUM: it deletes data files that no version inside a retention window still needs. PROTOCOL.md describes it as deleting unreferenced files "after a user-specified retention period (default 7 days)". Inside the window nothing is lost. Shrink the window and you choose which versions die.

LiveThe defaults, the safety check and the dry run2 min▶

The Databricks documentation gives two retention settings. delta.deletedFileRetentionDuration, default 7 days, is how long a tombstoned data file must be before VACUUM may delete it. delta.logRetentionDuration, default 30 days, is how long log entries are kept. Time travel to a version needs both its log entries and its data files, so the shorter of the two is your real horizon, and with defaults that is 7 days once VACUUM runs.

Asking for a retention shorter than the table's setting is blocked by a safety check, spark.databricks.delta.retentionDurationCheck.enabled, in Databricks; in delta-rs it is the enforce_retention_duration argument tonight's script turns off. VACUUM t DRY RUN lists what would be deleted (up to 1,000 files) without deleting anything. Databricks also offers VACUUM t LITE, which finds candidates from the log, alongside the default FULL mode.

LiveThe sentence to remember from the docs1 min▶

The Databricks VACUUM page puts it plainly: "If you run VACUUM on a Delta table, you lose the ability to time travel back to a version older than the specified data retention period." The retention you pass is a promise about which versions may still be read. Retention 0 promises only the latest one.

Self-studyWhy the one deleted file was the DELETE's output3 min▶

Replay the log the way session 2 taught. Version 2 removed A and B and added C. Version 3, the RESTORE, removed C and added A and B back. After version 3 the live set is A and B, and C is a tombstone: a file the latest version does not reference.

VACUUM with the default 7 days looks at C's tombstone, sees it is seconds old, and leaves it: dry run, 0 files. VACUUM with retention 0 and the check off treats every tombstone as expired, and C is the only one, so it deleted exactly 1 file. A and B survive because version 3 needs them. Version 2's entry is still in the log and still says "C is live", so reading version 2 asks for a file that is gone, and delta-rs raised FileNotFoundError. Nothing about the latest version changed: it still reads 77,033 rows.

Real world

Saving storage on a shared table. An engineer notices a shared trips table holds far more bytes than its live files account for, disables the retention check and runs VACUUM ... RETAIN 0 HOURS. The storage bill drops. The next morning a finance analyst's month-end notebook, which pins VERSION AS OF the version it reconciled against, fails with a missing file, and a teammate who wanted to RESTORE yesterday's state finds there is nothing left to restore to. This team is constructed; every step of the failure is what tonight's script does on your laptop.

VACUUM twice, then try to go back. First with the default retention, which finds nothing old enough. Then with retention forced to zero, which deletes the one file no live version needs. Then ask for version 2, which needed that file, and finally read the latest version with a different engine.

Check yourself

Three questions

Clear all three and analyst session 3 gets stamped in your passport.

1 · You run dt.restore(1) on a table at version 2. What does it write to the log?

Writers never overwrite or delete log entries, so undo is a new commit. Tonight's run printed version 3 with 77,033 rows, and the docs call RESTORE "a data-changing operation", which is why streaming readers may process the restored rows again.

2 · After the forced VACUUM, the latest version reads 77,033 rows but version 2 fails with FileNotFoundError. Why?

The log still says C is live at version 2, but the file is gone. A and B survive because version 3 needs them, which is why exactly 1 file was deleted and the latest read is unaffected.

3 · What is the default retention for deleted data files before VACUUM may remove them?

delta.deletedFileRetentionDuration defaults to 7 days, which PROTOCOL.md also gives as the VACUUM default. 30 days is the default for log entries, delta.logRetentionDuration, a different setting.
