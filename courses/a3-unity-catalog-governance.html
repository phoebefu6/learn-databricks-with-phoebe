Unity Catalog: who may see what

Session 2 showed that a Delta table remembers every change. That memory is only useful if the right people can read it and the wrong people cannot. On Databricks that job belongs to Unity Catalog: one tree that names every table, view, volume and model, and one set of rules for who may touch each branch. Tonight we read those rules the way a governance owner should, from the privileges reference itself, and turn them into a grant matrix a platform engineer could apply tomorrow morning.

Part 0

Where we start

Most access arguments in a data team are really naming arguments. Nobody can agree who should see "the customers table" because there are three of them, in three places, with three owners. Unity Catalog starts by fixing the names: every object has exactly one parent and therefore exactly one full name. Once the names are fixed, the access rules are short enough to fit on a sticky note, and three of them carry almost all the weight: the read rule, inheritance, and who may manage grants.

Part 1 · covers the three-level namespace

One tree for tables, volumes and models

5 min live

Unity Catalog organises everything as a tree. At the top sits the metastore; under it, catalogs; under each catalog, schemas; under each schema, the things people actually use: tables, views, volumes of files, and machine learning models. Each object hangs from exactly one parent, so its full name is always three parts long: catalog, schema, object.

Livecatalog.schema.table is the whole address2 min▶

The Databricks reference "Unity Catalog privileges and securable objects" names a table as catalog.schema.table. Everything the platform governs is a securable somewhere in that tree, and the tree has a single root: the metastore, which metastore admins oversee. In practice this means two things for a leader. First, "which customers table?" always has a precise answer, because two tables can only share a short name if they sit in different schemas or catalogs, and then their full names differ. Second, every grant has an address: it is attached to one node of the tree, and the rest of the session is about what that attachment reaches.

LiveModels live in the same tree2 min▶

The Databricks page "Manage model lifecycle in Unity Catalog" registers models under the same three-part pattern, <catalog>.<schema>.<model>, so a churn model is prod.ml.churn, a sibling of the tables it was trained on. The same doc says creating a model needs CREATE MODEL plus USE SCHEMA, loading one needs EXECUTE, and adding a version needs CREATE MODEL VERSION. The leader point: there is no second permission system for models. The person who decides who may read the training table also decides who may load the model, in the same place, with the same grammar. Analyst session 7 registers a real model and loads it by alias.

Self-studyWhat Free Edition gives you to practise on1 min▶

Databricks Free Edition is free, non-commercial and serverless only. Its limitations page (last updated 29 September 2026 when read) lists one workspace and one metastore per account, so you can practise catalogs, schemas and grants inside a single tree but not a multi-workspace layout. Limits change; re-check the limitations page before you plan a workshop around them.

Real world

Two "customers" tables, one tree (constructed). Sales and support each built a table called customers, in their own folders, with their own definitions of "active". For two years every dashboard argument began with "which one?". Moving both into one metastore did not merge them; it named them: sales.crm.customers and support.tickets.customers. The duplicate was suddenly visible in one search, each had a named owner, and the conversation moved from "who is right" to "which one do we certify".

Part 2 · covers the read rule and inheritance

Three keys to read one table

6 min live

Granting SELECT on a table is not enough to let anyone read it. The reader also needs permission to enter the catalog and the schema above it. And a grant made high in the tree flows down to everything below it, including objects that do not exist yet. Those two rules explain most of the access tickets a platform team ever sees.

LiveThe read rule, in the reference's own words2 min▶

To read a table, the privileges reference requires "SELECT on the table, USE CATALOG on the parent catalog, and USE SCHEMA on the parent schema". USE CATALOG and USE SCHEMA grant no data by themselves; they are the doors you must be allowed through to reach anything inside. That is why a familiar access ticket reads "I was granted SELECT and still cannot see the table": someone opened the last lock and forgot the first two. Teach your requesters the three keys and many of those tickets never need filing.

LiveInheritance flows down, into the future2 min▶

The same reference says a privilege granted on a catalog or schema applies to "all current and future objects" inside it. That is the most powerful rule in the system and the riskiest. Powerful, because one schema-level grant replaces hundreds of table grants and never needs updating when a new table lands. Risky, because the grant was decided for the tables you could see on the day you made it. A table added next quarter, perhaps one with salaries in it, inherits the same audience without anyone deciding that it should. The governance question is never only "who can read this schema today?" but "what are we agreeing to let into this schema later?"

Self-studyThe rule, run as a local model2 min▶

Analyst session 6 encodes the documented rule in a few lines of Python and runs it. It is a local model of the rule, not Unity Catalog itself, but its outputs make the logic concrete. With SELECT alone on main.taxi.trips, the analysts group gets "denied, missing USE CATALOG, USE SCHEMA". After USE CATALOG on main and USE SCHEMA on main.taxi are added: "can read". The finance group, granted SELECT on the whole schema plus the two doors, can read main.taxi.zones_created_next_year, a table that did not exist when the grant was made. The analysts group, holding SELECT only on trips, is told "denied, missing SELECT" for that same new table.

Real world

The schema that grew a payroll table (constructed). A finance analytics schema was opened to the whole finance group with one schema-level SELECT, a sensible decision for its eleven reporting tables. Eight months later an engineer landed a payroll extract in the same schema because "it is finance data". Nobody changed a grant, and the whole group could read every salary the same afternoon. The fix was not a new rule; it was a second schema with its own, narrower audience, and a standing question at design review: which schema does this table belong in, given who already reads that schema?

Part 3 · covers ownership and managing privileges

Owners, managers and admins

4 min live

Every securable has an owner, and the owner can grant on it. If the owner is one person, every access request in the organisation queues behind that person's inbox and holidays. Unity Catalog gives you a way to spread the work without handing over the object: the MANAGE privilege.

LiveOwners, and MANAGE without ownership2 min▶

The privileges reference describes MANAGE as the privilege that allows users to manage privileges, transfer ownership, rename, and drop an object, without being its owner. That is exactly the shape a governance function needs: the data product team owns the table, and a stewards group can answer access requests on it when the owners are busy, away or gone. Note one trap the reference spells out: ALL PRIVILEGES does not include MANAGE. Nor does it include READ METADATA, EXTERNAL USE SCHEMA or EXTERNAL USE LOCATION. Granting ALL PRIVILEGES to someone does not make them a manager, and it gives them far more data than most roles need.

LiveGrant to groups, not to people1 min▶

This one is standard practice rather than a sentence quoted from the reference, and it is practice for a good reason. A grant to a person is a decision you must remember to undo when they change role or leave. A grant to a group is a decision about the role; joining and leaving the group, usually handled by your identity team, does the rest. The same logic applies to ownership: a group owner never goes on holiday. Write every row of tonight's matrix as a group.

Self-studyWhere role design, row filters and masks live1 min▶

Tonight is the Databricks side: which securables exist, which privileges they take, and how grants travel through the tree. The concepts underneath, how to design roles, when attribute-based access beats role-based, and how row filters and column masks work as ideas, are taught in the data access control course. Read it before you design anything finer than the table level.

Real world

The owner who left (constructed). A senior engineer created the core sales tables in her own name and handled every access request herself, quickly and well. When she moved to another company, the tables kept working, and nobody could grant on them. For three weeks every new analyst waited while an admin worked out who should own what. The two-line fix, made afterwards for every table: ownership transferred to the sales data team's group, and MANAGE granted to a stewards group, so no single departure can freeze access again.

Build-along

Lay out the catalog and write the grant matrix

★ 22 min · everyone builds

No account needed. You design the tree for three teams, then fill a matrix whose rows are groups and whose columns are securables, one cell at a time, with the least privilege each group needs. Then you translate every cell into the statement a platform engineer would run. The first row is filled in for you as a constructed example.

Choose the catalog split. Two layouts are common. Split by environment (dev, prod) and the same schemas repeat in each catalog, so promoting work is a change of one name and production grants can be stricter than development ones. Split by domain (sales, finance) and each catalog mirrors an owning team, so ownership and budgets line up. Both are used; pick the one that matches how your organisation draws accountability, and write down why.

★ The layout decision, one paragraphSplit: by environment. Catalogs: dev, prod. Schemas in prod: sales (orders, returns), ml (models, training volumes). Why: production access is reviewed quarterly; dev access is broad. Owner of every catalog and schema: a group, never a person.

List three groups and the job each one does. Describe the work, not the wish list. "Reads orders for weekly reporting" leads to a privilege; "needs access to sales data" leads to an argument.

★ Three groups, written as workanalysts read prod.sales.orders for weekly reporting finance read every table in prod.sales, including new ones ml-engineers load the churn model prod.ml.churn in scoring jobs

Fill the matrix with the least privilege per cell. Start every reading row from the three keys and stop as soon as the job is covered. Leave a cell blank rather than writing a privilege "just in case".

★ The filled matrix catalog prod schema prod.sales table orders model churn analysts USE CATALOG USE SCHEMA SELECT - finance USE CATALOG USE SCHEMA, SELECT (inherited) - ml-engineers see doc - - EXECUTE (see doc)

Mark where inheritance gives more than intended. Every privilege written on a catalog or schema cell reaches all current and future objects underneath. Circle each one and write, beside it, the kind of table that would be a problem if it appeared there next year.

★ The inheritance checkfinance: SELECT on schema prod.sales reaches: orders, returns, and every table created there later risk: a customer-contact or salary extract landing in prod.sales control: sensitive extracts get their own schema; design review asks "who already reads the schema this table is joining?"

Write each cell as the statement it becomes. One cell, one line. For the model column, write it in words: the models-in-Unity-Catalog doc says loading a model needs EXECUTE on it, and your platform engineer applies that from the doc.

★ The analysts row, as GRANT statementsGRANT USE CATALOG ON CATALOG prod TO `analysts` GRANT USE SCHEMA ON SCHEMA prod.sales TO `analysts` GRANT SELECT ON TABLE prod.sales.orders TO `analysts` Model column, in words: ml-engineers need EXECUTE on prod.ml.churn to load it.
✗ The matrix that is one cell longGRANT ALL PRIVILEGES ON CATALOG prod TO `everyone` (every table, view, volume and model in prod, today and every one created later, for every user, and still no one who holds MANAGE)

Start from the read rule and add; never start from ALL PRIVILEGES and subtract. Subtraction depends on remembering everything the big grant included, today and in future. Addition depends only on knowing what the job needs, which you wrote down in step 2.

Homework

Before session 4

30 min
  1. Finish the matrix for all three groups and write every cell as a GRANT statement or, for models, a sentence.
  2. Find the last access ticket your team closed that said "granted, still cannot see it". Check whether the missing key was USE CATALOG or USE SCHEMA.
  3. List every object your organisation owns in one person's name, in any system. For each, name the group that should own it and the group that should be able to manage grants on it.

Check yourself

Three questions

Clear all three and leader session 3 gets stamped in your passport.

1 · An analyst has been granted SELECT on prod.sales.orders and nothing else. What happens when she queries it?

The reference requires SELECT on the table, USE CATALOG on the parent catalog and USE SCHEMA on the parent schema. The local model in analyst session 6 prints exactly this: "denied, missing USE CATALOG, USE SCHEMA".

2 · Finance holds SELECT on schema prod.sales. Next year an engineer creates a new table in that schema. Can finance read it?

Inheritance includes the future. That is why one schema grant can replace hundreds of table grants, and why "what might land in this schema later?" is a governance question, not an engineering detail.

3 · Your table owner is on leave for a month. What lets a stewards group handle access requests on her tables without taking ownership?

MANAGE is the privilege built for this. ALL PRIVILEGES does not include it, and also hands over every table in the catalog; SELECT only reads.
