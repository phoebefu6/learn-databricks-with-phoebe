Data skipping, OPTIMIZE and clustering

A query on a Delta table does not have to open every file. Each add in the log carries the minimum and maximum of the file's columns, and a reader that sees a filter can rule a file out before touching it. Tonight you load the whole of January 2024, 2,964,606 taxi trips, as 31 daily appends, write the skipping check yourself in six lines, and measure it before and after OPTIMIZE and Z-order. Then the part Databricks would want you to hear first: for new tables it recommends liquid clustering, which your laptop cannot run.

Part 1 · covers per-file statistics

Min and max decide what a query reads

5 min live

Session 2 showed that every add action can carry a stats field. The protocol says what it is for: "These statistics can be used for eliminating files based on query predicates". The rule is a single comparison. A filter pu_zone = 132 can only find rows in a file whose pu_zone range includes 132; every other file is skipped without being opened.

LiveWhat the log records about each file2 min▶

PROTOCOL.md lists the per-file statistics: numRecords, minValues, maxValues, nullCount and tightBounds. String statistics are cut to a prefix and timestamps are truncated to milliseconds. They live inside the add action in the JSON you read in session 2, so a reader can decide which files to skip by reading the log alone.

On Databricks, the data skipping page says statistics are collected on "the first 32 columns" by default for Unity Catalog external tables, while managed tables use predictive optimization to choose. Two table properties change the default: delta.dataSkippingNumIndexedCols (how many leading columns) and delta.dataSkippingStatsColumns (a named list, Databricks Runtime 13.3 LTS and above). "Long strings are truncated", so a filter on a long text column skips less than you might hope. The practical move: put the columns your queries filter on early in the schema, or name them.

LiveStatistics only help when the data is clustered2 min▶

The CIDR 2021 lakehouse paper names min-max statistics as auxiliary data "which enables data skipping optimizations when the base data is clustered". The last four words carry the whole session. In the figure, every daily file holds trips from all over the city, so its pu_zone range is wide and includes 132; the statistics are correct and useless for that query. The same files have narrow time ranges, because the loading pattern grouped trips by day. Statistics report the layout; they cannot fix it.

Self-studyWide bounds, tight bounds and null counts1 min▶

The tightBounds field says whether a file's min and max are exact. Bounds that are wider than the real data are still safe: they can only make a reader open a file it did not need, never skip a file that held a match. That asymmetry is the contract. A reader may over-read; it must never under-read. nullCount works the same way: a file whose count shows no nulls in a column can be skipped by an IS NULL filter on it. Session 8's bench has a button that deals the statistics to the wrong files, which is what an under-read looks like.

Real world

The dashboard that got slower as the month went on. An operations dashboard filters on pickup zone. The table behind it is loaded once a day, so by the 31st every query opens 31 files where it opened one on the 1st, and nobody changed a line of SQL. A second dashboard on the same table filters on yesterday's date and stays fast all month. This team is constructed; the two read counts are tonight's real 31 of 31 and 1 of 31.

Part 2 · covers OPTIMIZE and Z-order

Fewer files, then the right files

6 min live

OPTIMIZE does two different jobs that share a name. Compaction (bin-packing) rewrites many small files into fewer larger ones. Z-order rewrites them again, this time sorted so that each file covers a narrow range of the columns you name. Only the second changes which files a filter can skip. Both commit with dataChange false: the rows are the same, only their files move.

LiveCompaction: fewer files, same question2 min▶

The Databricks OPTIMIZE page describes bin-packing as idempotent: run it twice on the same data and the second run does nothing. It is the cure for many small files, and tonight it took 31 files to 8. It did nothing for JFK, which went from 31 of 31 to 8 of 8, still every byte. Each compacted file now covers a few days, so it still holds trips from every zone. The date query even got relatively worse: one file still, but a bigger one, 12.9 percent of the bytes instead of 2.7. Compaction is housekeeping, not clustering.

LiveZ-order, and the Delta paper's multi-column test3 min▶

Z-order sorts rows along a space-filling curve before writing, so each output file covers a narrow range of the chosen columns. With one column it is simply a sort, and JFK's trips land in one file of six: 17.9 percent of the bytes.

The point of the curve is several columns at once. The Delta Lake paper (Armbrust, Das, Sun, et al., PVLDB 2020, Figure 5) tested 100 Parquet objects with four uniformly random fields. A global sort on one of them let that field skip 99 percent of objects and the other three skip 0 percent. Z-order on all four skipped 67, 60, 47 and 44 percent, at least 43 percent on every field and 54 percent on average, against 25 percent for the single sort. Z-order spreads the benefit; it does not give any one column the full 99.

Self-studyThe trade you just made1 min▶

Sorting by zone scattered the days across every file. The 15 January query went from 1 of 8 files to 6 of 6. Nothing broke and no answer changed; the rows found are identical. What changed is which question is cheap. Session 8's bench shows the same pattern on a smaller sample, and adds the version where you cluster on a column nobody filters and lose on both questions.

Real world

A 500 TB table that skipped 93 percent. The Delta Lake paper reports a customer's network-traffic table of about 500 TB, Z-ordered on several fields, where queries skipped 93 percent of the data. This is the authors' own report of their customer, not an independent measurement, and the paper does not publish the queries. It is a fair picture of the upside when the clustering columns match how people actually filter.

Part 3 · covers liquid clustering

What Databricks recommends now

4 min live

Liquid clustering moves the choice of columns from the command into the table. You declare up to four keys once with CLUSTER BY, and every later OPTIMIZE clusters new data towards them. The protocol records the keys in the log: clustered tables carry a domainMetadata action in the domain delta.clustering, and clustered files carry clusteringProvider, for example "liquid".

LiveThe recommendation, in Databricks' own words2 min▶

The liquid clustering page says: "Databricks recommends liquid clustering for all new tables, including streaming tables and materialized views". The OPTIMIZE page goes further and recommends it "instead of partitions, ZORDER, or other data layout approaches". This is the vendor's recommendation for its own platform, and it is the default you should expect a Databricks team to follow.

The rules, from the same page: CLUSTER BY (col) on create, or ALTER TABLE ... CLUSTER BY later; at most four clustering keys; not compatible with partitioning or ZORDER on the same table. Runtime versions matter: liquid clustering needs Databricks Runtime 15.4 LTS or above, CLUSTER BY AUTO on Unity Catalog managed tables also 15.4 LTS or above, and OPTIMIZE ... FULL to recluster everything 16.4 LTS or above. These versions move; re-check the page before you rely on them.

LiveThe honest limit of the laptop path1 min▶

delta-rs 1.6.6 offers optimize.z_order and optimize.compact, not CLUSTER BY. So the build-along uses Z-order, and the liquid clustering step is Databricks only, labelled and not run. What carries over unchanged is the skipping itself: a liquid-clustered table is still read by comparing a filter with each file's min and max in the log. Clustering, however it is done, only changes which rows share a file.

Self-studyPredictive optimization1 min▶

On Unity Catalog managed tables, predictive optimization runs OPTIMIZE for you, and with CLUSTER BY AUTO it also chooses the keys from the queries it sees. That removes the scheduling chore, not the judgement: you still want to know which columns your heaviest queries filter on, so you can check what it picked. Scheduling OPTIMIZE yourself, on tables it does not manage, is an orchestration job: learn data orchestration covers schedules and retries.

Real world

The nightly job nobody remembered. A team runs OPTIMIZE ... ZORDER BY (customer_id) every night from a job written two years ago. The dashboards moved to filtering by region, but the column list lives only in the job's code. Moving the table to CLUSTER BY (region) puts the choice on the table itself, where DESCRIBE DETAIL shows it in clusteringColumns for anyone to review. This team is constructed. The detail behind it is real: in session 8's bench, the Z-order commit delta-rs wrote recorded the predicate and target size but not the columns.

★ b5.py, part 1# Analyst session 5: data skipping before and after OPTIMIZE and Z-order (no account needed) import json, shutil import duckdb, pyarrow as pa from deltalake import write_deltalake, DeltaTable shutil.rmtree("trips_month", ignore_errors=True) for d in range(1, 32): # one append per day: 31 small files day = duckdb.sql(f""" SELECT tpep_pickup_datetime AS pickup_ts, VendorID AS vendor_id, PULocationID AS pu_zone, trip_distance, fare_amount FROM 'yellow_tripdata_2024-01.parquet' WHERE tpep_pickup_datetime >= TIMESTAMP '2024-01-{d:02d}' AND tpep_pickup_datetime < TIMESTAMP '2024-01-{d:02d}' + INTERVAL 1 DAY """).arrow().read_all() write_deltalake("trips_month", day, mode="append")

Write the skipping check and measure the daily layout. get_add_actions(flatten=True) returns one row per live file with columns such as min.pu_zone, max.pu_zone and size_bytes, read straight from the log. files_read keeps a file unless its range lies wholly below or wholly above the filter. No data file is opened to make the decision.

★ b5.py, part 2def files_read(path, col, lo, hi): """Data skipping by hand: read a file only if [min, max] can overlap [lo, hi].""" acts = pa.table(DeltaTable(path).get_add_actions(flatten=True)).to_pylist() read = [a for a in acts if not (a[f"max.{col}"] < lo or a[f"min.{col}"] > hi)] return len(read), len(acts), sum(a["size_bytes"] for a in read), sum(a["size_bytes"] for a in acts) def report(tag): j = files_read("trips_month", "pu_zone", 132, 132) import datetime as dt d = files_read("trips_month", "pickup_ts", dt.datetime(2024, 1, 15), dt.datetime(2024, 1, 15, 23, 59, 59)) print(f"{tag:22s} JFK: {j[0]}/{j[1]} files, {100*j[2]/j[3]:.1f}% of bytes | 15 Jan: {d[0]}/{d[1]} files, {100*d[2]/d[3]:.1f}% of bytes") print("rows:", DeltaTable("trips_month").count() if hasattr(DeltaTable, "count") else "") report("31 daily appends")

Check yourself

Three questions

Clear all three and analyst session 5 gets stamped in your passport.

1 · For the filter pu_zone = 132, when can a reader skip a file without opening it?

The test compares the filter with the file's min and max in the log. If the range cannot contain 132, no row in the file can match, so the file is skipped. Any other file must be opened.

2 · Compaction took the table from 31 files to 8, yet the JFK query still read 8 of 8. Why?

Bin-packing joins files; it does not sort rows. The new files cover a few days each and still span the whole city, so the statistics cannot rule any of them out. Z-order on pu_zone took the same query to 1 of 6.

3 · What does Databricks recommend for new tables, and why does the laptop path use Z-order instead?

Databricks recommends liquid clustering for all new tables, including streaming tables and materialized views, with at most four keys. The laptop library cannot run it, so the build-along uses Z-order; the skipping mechanism underneath is the same min and max check.
