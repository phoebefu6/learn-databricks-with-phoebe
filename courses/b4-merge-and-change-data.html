MERGE and change data

Real tables do not only grow. Tips get corrected, trips get cancelled, and cabs that lost their connection send yesterday's trips late. Tonight you apply all three kinds of change to a Delta table in a single MERGE that lands as one commit, then ask the table itself what changed and get back a ledger of every deleted, inserted and updated row. On the way you trip two traps on purpose: a source with two rows for one trip, which Delta refuses, and a NULL flag that quietly loses 2,865 trips if you are not looking.

Part 1 · covers MERGE

Insert, update and delete in one commit

6 min live

MERGE joins a source to a target on a key and then decides, row by row, which clause applies. Tonight's source is a feed of real trip rows, each tagged with an op: U for a tip correction, D for a cancellation, I for a late trip. The target is the table of on-time trips. The join key is trip_id. Everything the MERGE does lands in one new log entry, so readers see either none of the feed or all of it.

LiveThe clauses, in SQL and in delta-rs3 min▶

The Databricks MERGE documentation names three kinds of clause. WHEN MATCHED fires when a source row finds a target row on the join condition; it can UPDATE or DELETE. WHEN NOT MATCHED fires when a source row finds nothing; it can only INSERT. WHEN NOT MATCHED BY SOURCE fires for target rows that no source row touched, which is how you delete what a full snapshot no longer contains. Each clause can carry an extra condition, like AND s.op = 'D', and that is what lets one statement apply a mixed feed.

The deltalake package spells the same thing as a builder: DeltaTable(...).merge(source, predicate, source_alias="s", target_alias="t"), then .when_matched_delete(predicate=...), .when_matched_update(updates=..., predicate=...), .when_not_matched_insert_all(predicate=...), and finally .execute(), which returns a dictionary of counts. Nothing is written until execute().

LiveThe feed is constructed, the trips are real2 min▶

Be clear with your room about what is real here. The 275 late trips are genuine: they are the 15 January trips whose store_and_fwd_flag is 'Y', meaning the cab held the record in memory because it had no server connection and sent it later. The script holds them back from the first load and feeds them in as inserts, which is exactly how they arrive in life. The 5 tip corrections and 3 cancellations are made up: the script picks real trips by position and invents the change. So the counts are real outputs of a constructed feed.

Self-studyWhat MERGE does to the files2 min▶

Parquet files are never edited in place, so MERGE rewrites the files that hold matched rows: it writes new files with the changes applied, and the commit removes the old ones and adds the new ones. On the bench in analyst session 8, a MERGE of 31 late trips and 270 re-sent trips into a 31-file table removed 1 file and added 1, plus one cdc file for the change feed. How many files a MERGE touches depends on how many files hold matching keys, which is why session 5's layout work matters for MERGE cost too.

Real world

The batch that arrived twice. On the bench, the trips of 12 January are loaded once and then sent again, 270 of them, as a constructed uploader retry. An append would have doubled them. Merged on trip_id, the re-sent rows match existing rows and are rewritten into a new file rather than duplicated, the 31 late trips insert, and the table ends at exactly 8,000 rows, the size of the sample. No duplicates, because the key decided, not the arrival count. Open the bench to see that commit as version 31.

Part 2 · covers the change data feed

The table tells you what changed

5 min live

After a MERGE, a downstream job needs to know which rows moved. Re-reading the whole table and diffing it is slow and fragile. The change data feed, switched on with a table property, makes the table keep its own ledger: every changed row, tagged with the kind of change and the commit that made it.

LiveSwitching it on, and what you get back2 min▶

The Databricks change data feed documentation is plain about three things. It is not on by default: you set delta.enableChangeDataFeed = true on the table. It records only changes made after you switch it on, so turn it on at creation if anyone will ever ask "what changed". And each change row carries three extra columns: _change_type, _commit_version and _commit_timestamp. In SQL you read a range of versions with table_changes('t', 0, 10); in delta-rs with DeltaTable(...).load_cdf(starting_version=...).

There are four change types. insert and delete are one row each. An update produces two rows: update_preimage, the row as it was, and update_postimage, the row as it is now. That is why tonight's 5 tip corrections appear as 10 change rows, and why a consumer can compute the size of each correction without looking anywhere else.

LiveWhere the feed lives in the protocol2 min▶

PROTOCOL.md puts change data files in a _change_data folder next to the data files, and records them in the log as cdc actions with dataChange false: they describe a change, they are not part of the table's rows. A reader asked for changes uses the cdc files when a commit has them; when it does not, as with a plain append, the reader treats the commit's added files as inserts and its removed files as deletes. Checkpoints never keep cdc actions, so the feed is read from the JSON commits.

Self-studyHow long the feed lasts, and who consumes it1 min▶

The feed is not an archive. The documentation notes that VACUUM deletes change data files too, under the same retention rules you met in session 3, so a consumer that falls behind the retention window loses changes it never read. Reading the feed continuously, as a stream that picks up each new commit, is streaming work: see Learn streaming data with Phoebe. Building the downstream pipeline that applies those changes elsewhere belongs to Learn data engineering with Phoebe. Here you only need to know the feed exists, what it holds, and when it disappears.

Part 3 · covers two traps

The duplicate and the NULL

4 min live

Two things go wrong with change data again and again. One fails loudly: a source with two rows for the same key. The other fails silently: a filter that treats a missing flag as if it were a value. You meet both tonight, on purpose, so you recognise them when they turn up uninvited.

LiveDeduplicate the source first2 min▶

The Databricks MERGE documentation states the rule directly: "A merge operation can fail if multiple rows of the source dataset match and the merge attempts to update the same rows of the target". Two source rows for trip X carry two different tips; MERGE has no honest way to pick one, so it refuses rather than picking by row order. In tonight's run delta-rs raises DeltaError and the table stays at version 1. The documented fix is to deduplicate the source before the MERGE: keep one row per key, chosen by a rule you can defend, such as the latest event timestamp in the feed.

LiveThe NULL trap, and the fix1 min▶

On 15 January the flag reads N for 73,893 trips, Y for 275 and NULL for 2,865. "Every trip that was not sent late" sounds like store_and_fwd != 'Y'. But in SQL, NULL != 'Y' is not true, it is NULL, and a filter keeps only rows where the condition is true. So the filter returns 73,893 rows and the 2,865 NULL rows vanish without an error. The script decides explicitly what NULL means, on time, with pc.fill_null(pc.equal(base["store_and_fwd"], "Y"), False) before inverting, and loads 76,758.

Self-studyWhy both traps bite harder in change data1 min▶

A change feed that is retried after a failure delivers some rows twice, by design: the sender cannot know which rows got through, so it sends them again. That makes duplicate keys normal in CDC sources, not exotic. And change feeds are where nullable status flags live: an op code, a deleted marker, a late flag. Any filter on such a flag needs an explicit rule for NULL, written down next to the filter, because the default rule drops rows quietly.

Real world

This build fell into the second trap. The first draft of b4.py, written for this session, filtered on-time trips with != 'Y' and loaded 73,893 trips instead of 76,758. Nothing failed. It was caught only because 73,893 plus the 275 late trips did not add up to 77,033, the day's total from session 1. This is a true story of building these materials, and the reason the tip below exists.

Build-along

Merge a change feed, then read what changed

★ 22 min · everyone builds

Work in a folder that holds the January file from session 1 (or fetch it again with the command there). Run b4.py in five parts. The outputs shown are what the laptop path printed when this build ran it with deltalake 1.6.6 and DuckDB 1.5.6; the feed is built from fixed row positions, so your counts should match.

Load one day and hold the late trips back. Each trip gets a trip_id from a fixed ordering, so the key is stable across runs. The late trips are the real store-and-forward ones; note the fill_null, which is the fix from Part 3. The table is created with the change data feed already on.

★ b4.py, part 1# Analyst session 4: MERGE a change feed, then read the change data feed (no account needed) import shutil import duckdb, pyarrow as pa, pyarrow.compute as pc from deltalake import write_deltalake, DeltaTable shutil.rmtree("trips_cdf", ignore_errors=True) base = duckdb.sql(""" SELECT row_number() OVER (ORDER BY tpep_pickup_datetime, tpep_dropoff_datetime, PULocationID, DOLocationID, fare_amount, trip_distance, VendorID, tip_amount) AS trip_id, tpep_pickup_datetime AS pickup_ts, PULocationID AS pu_zone, fare_amount, tip_amount, store_and_fwd_flag AS store_and_fwd FROM 'yellow_tripdata_2024-01.parquet' WHERE tpep_pickup_datetime >= TIMESTAMP '2024-01-15' AND tpep_pickup_datetime < TIMESTAMP '2024-01-16' """).arrow().read_all() late = base.filter(pc.equal(base["store_and_fwd"], "Y")) # sent late by the cab: real ontime = base.filter(pc.invert(pc.fill_null(pc.equal(base["store_and_fwd"], "Y"), False))) # null flag = on time write_deltalake("trips_cdf", ontime, configuration={"delta.enableChangeDataFeed": "true"}) print("loaded:", ontime.num_rows, "trips; held back as late:", late.num_rows)
Output · laptop path, deltalake 1.6.6loaded: 76758 trips; held back as late: 275

Build the change feed. Constructed on real rows: five trips get a tip one dollar higher, three are marked cancelled, and every late trip becomes an insert. Each row carries its op.

★ b4.py, part 2# the change feed (constructed on real rows): 5 tip corrections, 3 cancellations, the late trips fix = ontime.slice(100, 5).to_pylist() for r in fix: r["tip_amount"] = round(r["tip_amount"] + 1.0, 2); r["op"] = "U" cancel = ontime.slice(200, 3).to_pylist() for r in cancel: r["op"] = "D" ins = late.to_pylist() for r in ins: r["op"] = "I" feed = pa.Table.from_pylist(fix + cancel + ins)

Apply it in one MERGE. Three clauses, each guarded by the op. Nothing is written until execute(), and then exactly one commit is.

★ b4.py, part 3m = (DeltaTable("trips_cdf").merge(feed, "t.trip_id = s.trip_id", source_alias="s", target_alias="t") .when_matched_delete(predicate="s.op = 'D'") .when_matched_update(updates={"tip_amount": "s.tip_amount"}, predicate="s.op = 'U'") .when_not_matched_insert_all(predicate="s.op = 'I'") .execute()) print("merge:", {k: m[k] for k in ("num_target_rows_inserted", "num_target_rows_updated", "num_target_rows_deleted")})
Output · laptop path, deltalake 1.6.6merge: {'num_target_rows_inserted': 275, 'num_target_rows_updated': 5, 'num_target_rows_deleted': 3}

Ask the table what changed. Read the change data feed from version 1, the MERGE, and count the rows by change type.

★ b4.py, part 4cdf = pa.table(DeltaTable("trips_cdf").load_cdf(starting_version=1)) print("change rows by type:", duckdb.sql("SELECT _change_type, count(*) n FROM cdf GROUP BY 1 ORDER BY 1").fetchall())
Output · laptop path, deltalake 1.6.6change rows by type: [('delete', 3), ('insert', 275), ('update_postimage', 5), ('update_preimage', 5)]

Break it on purpose. A source with two rows for the same trip, with two different tips. The MERGE is refused and the version does not move.

★ b4.py, part 5# a source with two rows for one target row is refused, not guessed at dup = pa.Table.from_pylist([dict(fix[0]), dict(fix[0], tip_amount=99.0)]) try: (DeltaTable("trips_cdf").merge(dup, "t.trip_id = s.trip_id", source_alias="s", target_alias="t") .when_matched_update(updates={"tip_amount": "s.tip_amount"}).execute()) print("duplicate source merged without error") except Exception as e: print("duplicate source refused:", type(e).__name__) print("version now:", DeltaTable("trips_cdf").version())

★ Free Edition, SQL cell (not run in this build)ALTER TABLE your_catalog.your_schema.trips_cdf SET TBLPROPERTIES (delta.enableChangeDataFeed = true); MERGE INTO your_catalog.your_schema.trips_cdf AS t USING your_catalog.your_schema.trips_feed AS s ON t.trip_id = s.trip_id WHEN MATCHED AND s.op = 'D' THEN DELETE WHEN MATCHED AND s.op = 'U' THEN UPDATE SET t.tip_amount = s.tip_amount WHEN NOT MATCHED AND s.op = 'I' THEN INSERT (trip_id, pickup_ts, pu_zone, fare_amount, tip_amount, store_and_fwd) VALUES (s.trip_id, s.pickup_ts, s.pu_zone, s.fare_amount, s.tip_amount, s.store_and_fwd); SELECT _change_type, count(*) FROM table_changes('your_catalog.your_schema.trips_cdf', 1) GROUP BY 1;

Reconcile the totals before you trust a MERGE. Write down the number you expect before the run and check it after: tonight, 76,758 on time plus 275 late must equal the day's 77,033. A refused MERGE tells you it failed; a lost NULL or a doubled insert never does, and a sum that does not reconcile is often the only alarm you get.

Check yourself

Three questions

Clear all three and analyst session 4 gets stamped in your passport.

1 · The change feed for tonight's MERGE shows 5 rows of type update_preimage. What are they?

An update is reported as two rows: the old version (preimage) and the new one (postimage), both with the MERGE's _commit_version. That is why 5 corrections produce 10 change rows.

2 · A source holds two rows for the same trip_id with different tips. Why does the MERGE refuse instead of applying one?

The MERGE docs say a merge can fail when multiple source rows match and try to update the same target row. Picking one would be decided by row order. Deduplicate the source first with a rule you choose.

3 · Filtering on-time trips with store_and_fwd != 'Y' returned 73,893 rows, not 76,758. Where did the 2,865 trips go?

A filter keeps rows where the condition is true. A comparison with NULL gives NULL, not true. Decide what NULL means explicitly, as the script does with fill_null, and reconcile the total.
