Delta tables by hand

A Delta table sounds like a database object. On disk it is a folder: ordinary Parquet files, and next to them a _delta_log folder of numbered JSON files that say which Parquet files count. Tonight you build one from a real day of New York taxi trips, on your own laptop with the open-source deltalake package, no account and no cluster. You append to it, read it with three different engines, and watch it refuse a write that would break it. Then you see the same moves in Databricks Free Edition, where the platform does the folder-keeping for you.

Part 1 · covers what a Delta table is on disk

A folder, some Parquet, and a log

6 min live

The Delta protocol, published as PROTOCOL.md in the delta-io repository, describes the table entirely as files. Data files hold the rows in Parquet. Log entries, JSON files in _delta_log "named using the next available version number, zero-padded to 20 digits", say which data files make up each version. Nothing else is required: no server, no metastore.

LiveData files and log entries3 min▶

A data file is plain Parquet: columnar, compressed, readable by almost anything. Delta never edits one. A log entry is a JSON file whose lines are actions; version 0 holds four of them in tonight's table: commitInfo (what happened), protocol (which reader and writer features are needed), metaData (the schema and settings) and add (one data file joins the table, with its size and statistics). Version 1 holds just commitInfo and one add.

The protocol calls log entries "the unit of atomicity for a table". A commit either exists as a complete JSON file or does not exist at all, which is how a folder of files gets the all-or-nothing behaviour of a database transaction. Session 2 opens these files line by line.

Self-studyWhy three engines agree without talking2 min▶

DuckDB's delta extension, polars and the deltalake package are three separate implementations. They agree on 77,033 rows because each one reads the same log and follows the same rule for which files are live. That is the practical meaning of an open table format: the table's truth lives in files anyone can read, not inside one engine's memory. It is also why a team can write with Spark on Databricks and read with DuckDB on a laptop, as long as both understand the table's protocol version.

Real world

A Parquet folder with no log. A team lands daily Parquet files in a bucket and points two tools at the folder. A load fails halfway and leaves three of its five files behind. One tool counts the partial day, the other has a cached file list and does not, and the two dashboards disagree for a week. With a log, the half-written files are never added by a commit, so no reader treats them as part of the table. The Delta Lake paper describes this exact class of problem: object stores make multi-object updates non-atomic. This team is constructed; the failure mode is the reason the format exists.

Part 2 · covers writing, appending and schema enforcement

Every write is a commit, and some are refused

5 min live

write_deltalake has four modes: error (the default, create the table or fail if it exists), append, overwrite and ignore. Each successful call writes new Parquet files first and then one new log entry. If the new rows do not fit the table's schema, the call fails before any log entry is written, so the table does not change.

LiveSchema enforcement, and when you want evolution instead3 min▶

The CIDR 2021 lakehouse paper lists schema enforcement among the quality features a metadata layer makes natural: the layer knows the schema, so it can reject records that do not match. In tonight's run a single row with a text fare is refused with SchemaMismatchError and DeltaTable("trips_delta").version() still returns 1.

Sometimes a new column is legitimate. write_deltalake takes schema_mode="merge" to add new columns to the table schema in the same commit, and schema_mode="overwrite" together with mode="overwrite" to replace it. Both are deliberate choices recorded in the log, never accidents.

Self-studyWhat version 0 recorded about the protocol2 min▶

Tonight's table stores pickup_ts as a timestamp with no time zone, because the TLC file records local New York time without one. delta-rs therefore wrote "minReaderVersion":3,"minWriterVersion":7 with the feature timestampNtz in version 0. Any engine that reads the table must support that feature. Protocol versions are how a Delta table says "you need at least this much reader to understand me", and session 2 shows them in the raw JSON.

Part 3 · covers the laptop path and the Free Edition path

Same table idea, two places to build it

4 min live

On the laptop you own the folder and pick the engines. In Databricks the folder still exists, in cloud storage, but Unity Catalog names it catalog.schema.table, tracks who may read it, and Spark or SQL writes the commits. Databricks Free Edition gives you that environment at no cost for learning: serverless compute only, one SQL warehouse limited to 2X-Small, at most 5 concurrent job tasks, non-commercial use.

LiveWhat Free Edition is, and what it is not2 min▶

Databricks describes Free Edition as "perpetually free" and built for "students, hobbyists, and aspiring data and AI professionals"; it replaced the retired Community Edition. Its limitations page lists serverless compute only, one 2X-Small SQL warehouse, 5 concurrent job tasks, outbound internet restricted to trusted domains, one workspace, and non-commercial use only. If you exceed the usage quota, compute shuts down "for the rest of the day (and in extreme cases, the rest of the month)". Re-read that page before you teach from it; the limits change.

Self-studyManaged tables and why you rarely see the folder2 min▶

In Databricks you usually create a managed table: Unity Catalog chooses where its files live and handles their lifecycle, and you refer to it only by its three-part name. The files and the _delta_log are still there, which is why DESCRIBE DETAIL reports a location, a format of delta and a count of files, and why DESCRIBE HISTORY returns one row per commit. Session 3 reads that history; session 6 covers the permissions.

Build-along

Your first Delta table, from one real day

★ 22 min · everyone builds

Make an empty folder, put the January file in it, and run each step. The outputs shown are what the laptop path printed when this build ran it with deltalake 1.6.6 and DuckDB 1.5.6. File names inside the folder contain random ids, so yours will differ there and nowhere else.

Install the pinned versions and fetch the data. Work in a new empty folder. The file is public; no account or key is needed.

★ Terminalpip install deltalake==1.6.6 duckdb==1.5.6 polars==1.44.2 pyarrow==25.0.1 pandas==3.0.6 curl -O https://d37ci6vzurychx.cloudfront.net/trip-data/yellow_tripdata_2024-01.parquet

Select one day and split it at noon. DuckDB reads the Parquet file in place. The columns are renamed to what the rest of the track uses.

★ b1.py, part 1import os, shutil import duckdb, polars as pl from deltalake import write_deltalake, DeltaTable shutil.rmtree("trips_delta", ignore_errors=True) SQL = """ SELECT VendorID AS vendor_id, tpep_pickup_datetime AS pickup_ts, PULocationID AS pu_zone, DOLocationID AS do_zone, trip_distance, fare_amount, tip_amount, payment_type FROM 'yellow_tripdata_2024-01.parquet' WHERE tpep_pickup_datetime >= TIMESTAMP '{a}' AND tpep_pickup_datetime < TIMESTAMP '{b}' """ morning = duckdb.sql(SQL.format(a="2024-01-15 00:00", b="2024-01-15 12:00")).arrow().read_all() evening = duckdb.sql(SQL.format(a="2024-01-15 12:00", b="2024-01-16 00:00")).arrow().read_all() print("morning rows:", morning.num_rows, " afternoon and evening rows:", evening.num_rows)
Output · laptop path, deltalake 1.6.6morning rows: 21617 afternoon and evening rows: 55416

Create the table, append to it, and look in the folder. The first call creates version 0; the append is version 1.

★ b1.py, part 2write_deltalake("trips_delta", morning) # creates the table: version 0 write_deltalake("trips_delta", evening, mode="append") # version 1 dt = DeltaTable("trips_delta") print("version:", dt.version()) print("data files:", len(dt.file_uris())) print(sorted(os.listdir("trips_delta/_delta_log")))
Output · laptop path, deltalake 1.6.6version: 1 data files: 2 ['00000000000000000000.json', '00000000000000000001.json']

Read it with three engines. DuckDB installs its delta extension on first use, polars and pandas go through delta-rs. None of them is told how many files there are.

★ b1.py, part 3print("DuckDB rows:", duckdb.sql("INSTALL delta; LOAD delta; SELECT count(*) FROM delta_scan('trips_delta')").fetchone()[0]) print("polars rows:", pl.read_delta("trips_delta").height) print("pandas rows:", len(dt.to_pandas()))
Output · laptop path, deltalake 1.6.6DuckDB rows: 77033 polars rows: 77033 pandas rows: 77033

Break it on purpose. Append one row whose fare is text. The write is refused and the version does not move.

★ b1.py, part 4bad = pl.DataFrame({"vendor_id": [1], "fare_amount": ["twelve dollars"]}).to_arrow() try: write_deltalake("trips_delta", bad, mode="append") except Exception as e: print("refused:", type(e).__name__) print("version after the refused write:", DeltaTable("trips_delta").version())
Output · laptop path, deltalake 1.6.6refused: SchemaMismatchError version after the refused write: 1

✗ The habit that breaks a Delta tablerm trips_delta/part-00000-*.parquet # "cleaning up" files by hand cp new_day.parquet trips_delta/ # adding files without a commit # the log still lists the deleted file and never lists the new one

Touch the folder only through the log. A file you add by hand is invisible to every reader; a file you delete by hand makes the table unreadable at every version that lists it. Writes, deletes and cleanup all go through commands that write a commit, which sessions 2 and 3 take apart.

Check yourself

Three questions

Clear all three and analyst session 1 gets stamped in your passport.

1 · What makes the folder trips_delta a Delta table rather than a folder of Parquet files?

The data files are ordinary Parquet. The log is the table: it defines versions, schema, protocol and which files count. Without it, the files are just files.

2 · An append with a text fare fails with SchemaMismatchError. What is the table's version afterwards, and why?

No commit, no change. The refused write may leave nothing behind or an orphan file at most, and no reader will ever treat an uncommitted file as part of the table.

3 · DuckDB, polars and pandas all report 77,033 rows. Why can three separate engines agree without coordinating?

An open table format puts the table's truth in readable files. Any engine that implements the protocol arrives at the same set of live files, and therefore the same rows.
