The Delta log bench

Everything the analyst track built by hand comes together on one real table. 8,000 real New York taxi trips from January 2024 went through 37 commits, written by delta-rs: a load per day, a MERGE, a DELETE, an OPTIMIZE, and two different Z-order rewrites. The bench in this page holds the _delta_log those commits produced and replays it in your browser exactly as the Delta protocol tells a reader to. Pick a version and it rebuilds the live file set. Write a predicate and it shows which files data skipping reads, how many bytes that is, and whether the answer matches a full scan. Then press the break button and watch a fast answer become a wrong one.

Part 0

Where we start

A bench is a fixed table and a fixed set of questions, so that when two layouts give two answers the layout is the only thing that changed. The rows are real: a seeded sample of 8,000 trips from the TLC's public January 2024 yellow taxi file. The log is real: every JSON line was written by the open-source deltalake package, version 1.6.6, and nothing in it was edited. Two things are scaled or constructed, and the widget says so: files target 28 KB so that 8,000 rows make several files, and the re-sent 12 January batch in the MERGE is a retry made up for the lesson.

🎫 Clear all three quiz questions to stamp your passport real = replayed from the log delta-rs wrote the break button = the same stats, dealt to the wrong files

★ What you walk out with tonight. The habit of asking two questions of any Delta table: "which files are live at the version I am reading?" and "which of them does my filter actually read?", plus three measured facts to argue with: clustering on the column you filter turns 8 of 8 files into 2 of 8, clustering on a column nobody filters buys nothing and costs the date query, and statistics that lie give a fast wrong answer with no error.

Part 1 · covers how the table was built

Thirty-seven commits, declared in advance

6 min live

The sequence was fixed before any number was looked at, so nothing was tuned to make a point. Each box below is one JSON file in _delta_log. From version 33 the table was copied twice, so the two version 34 commits are two answers to the same question: which column should the files be clustered by?

LiveFive decisions, stated once3 min▶

Real rows, sampled once. 8,000 trips drawn uniformly from the 2,964,606 January pickups with seed 20240101 and numbered 1 to 8,000 in pickup order. The trip id is ours; the TLC file has none.

One append per pickup day, the way a nightly load writes, so each early file holds exactly one day. Trips with store_and_fwd_flag = 'Y', which the cab kept in memory because it had no connection, were held back: 31 of them.

The MERGE inserts those 31 late trips and matches a re-sent copy of all 270 trips from 12 January. The re-send is constructed, an uploader retry, and it is there because a retried batch is the most common reason a MERGE runs at all. Matching on trip_id means the retry adds no duplicates.

The DELETE removes the 113 trips with a fare below zero, which in the TLC data are voided or refunded records. It touched 30 of the 31 files, because voided trips happen on almost every day.

Files are scaled down. 28 KB per file, set as delta.targetFileSize and as the OPTIMIZE target, so 8,000 rows make 8 files after compaction. Real tables aim for much larger files; the mechanism is the same at any size.

Self-studyWhat the replay does, in four rules2 min▶

The engine in this page follows the "Action Reconciliation" section of the Delta protocol. Read the commits in version order. An add makes a file live, a remove turns it into a tombstone, the latest protocol and metaData win, and a cdc action points at change data, never at table data. From version 32 on it starts from the checkpoint delta-rs wrote and reads only the commits after it, then checks that a replay of every commit from version 0 gives the same live files. It always does; the line under the break button says so for the version you are on.

Before any number here was written down, the same replay was run in Python against delta-rs's own file list for every version of both branches, and against a full read of the table for every preset question: 370 checks, no disagreement.

Build-along · the bench

Versions, predicates and the break button

★ 26 min · the main event

Work through the four moves below in order. Each one is a question you answered by hand in an earlier session; tonight the answer comes from the real log in front of you.

Time travel. Drag the version slider from 0 to 34 with the JFK preset on. Watch the live file count climb by one a day to 31, hold at 31 through the MERGE, fall to 9 at the DELETE and 8 at the OPTIMIZE. Say out loud why version 31 still has 31 files when it added 31 trips: the MERGE removed one file and added one.

★ What to read off the commit linev31 MERGE 1 add, 1 remove, 1 cdc 31 live files v32 DELETE 8 add, 30 remove, 1 cdc 9 live files v33 OPTIMIZE 1 add, 2 remove, dataChange false 8 live files

Data skipping on the daily layout. At version 30, run "Picked up on 15 January", then "Picked up at JFK Airport". The date query reads 1 of 31 files and 2.7 percent of the bytes, because one file holds one day and the stats say so. The JFK query reads 31 of 31: every day has some JFK pickups.

Cluster, then cluster wrong. Move to version 34 with "Z-order by pu_zone": JFK drops to 2 of 8 files and 26.5 percent of bytes, and 15 January rises to 8 of 8. Switch to "Z-order by vendor_id": JFK stays at 8 of 8, and 15 January is still 8 of 8. Then slide to 35 and watch RESTORE give the version 33 layout back.

★ The ladder, as the bench prints it JFK 15 January v30 31 daily files 31 of 31 1 of 31 v33 compacted 8 of 8 2 of 8 v34 by pu_zone 2 of 8 8 of 8 v34 by vendor_id 8 of 8 8 of 8

Break it. On version 34 by pu_zone with JFK selected, press the break button. The same eight min/max pairs are dealt to the wrong files. The query still reads 2 files, still runs fast, and returns 0 of the 358 JFK trips a full scan finds. Then try your own predicate with the break on, and find one where the answer survives by luck.

Read it in this order. Files read, then share of bytes, then the two row counts side by side. A skipping result is only good news when the last two numbers match; the bench prints both so that a fast answer can never hide a wrong one.

Part 2 · covers what layout does to skipping

Clustering chooses which question gets cheap

6 min live

Data skipping reads a file unless its min and max prove it holds no match. So the work skipping saves depends entirely on how tightly each file's values are bunched for the column in the filter. The bench measures that for two questions across four layouts.

LiveFinding 1: the daily load was already a layout2 min▶

Nobody chose to cluster the table by date, yet at version 30 the date query reads one file in 31. Appending one day at a time put each day in its own file, so the pickup_ts min and max of each file are one day apart. Compaction keeps most of that order, which is why 15 January still costs only 2 of 8 files at version 33. Every table has a layout; the only question is whether anyone chose it.

LiveFinding 2: clustering trades one question for another2 min▶

Z-ordering by pu_zone sorts the trips by zone before writing, so each file covers a narrow band of zones: 4 to 88, 88 to 132, 132 to 142, and so on. JFK falls in two files because 132 sits on a boundary, and the query reads 26.5 percent of the bytes. The same rewrite scatters the days across all eight files, so the date query that cost 2 files now costs 8. A layout is a decision about which questions get cheap. Session 5 showed the same trade on the whole month: 1 file of 6 for JFK, 6 of 6 for the date.

Self-studyFinding 3: the multi-column answer, and what Databricks recommends now2 min▶

Z-order on several columns exists to soften that trade. In the Delta Lake paper's own test, a single sort let one column skip 99 percent of 100 objects and the other three skip nothing, while Z-order on all four skipped between 44 and 67 percent on each, 54 percent on average against 25. For new tables Databricks now recommends liquid clustering instead of Z-order: CLUSTER BY up to four keys, reclustered incrementally by OPTIMIZE, and, on Unity Catalog managed tables, CLUSTER BY AUTO lets predictive optimization pick the keys from the queries it sees. The skipping it enables is the same min/max mechanism this bench measures; delta-rs offers Z-order, not CLUSTER BY, so the bench stays with Z-order.

Part 3 · covers the anti-lever and the break button

Fast, and wrong

5 min live

Data skipping is safe because of one promise: a file's min and max really bound its values. The break button keeps every statistic and only deals them to the wrong files, using the same fixed shuffle in Python and in the browser. Nothing about the query looks different. The answer is.

LiveThe anti-lever, stated with its nuance2 min▶

Clustering by vendor_id is a real OPTIMIZE that rewrites all eight files, costs the same compute as the useful one, and changes nothing for any query here: vendor_id has only three values in the whole month, so sorting by it leaves every file spanning nearly every zone and every day. It does not make the JFK query slower; it leaves it at 8 of 8. It does make the date query slower, 2 of 8 to 8 of 8, because it threw away the order the daily loads had given for free. That is the honest size of the mistake: wasted work plus one lost advantage, not a disaster. RESTORE at version 35 undoes it with a new commit, and the bench shows the version 33 file set returning.

LiveWhat the break button proves, and where it cannot bite2 min▶

With the stats shuffled, JFK at version 34 by zone returns 0 of 358, 15 January at version 33 returns 0 of 186, and the JFK week at version 30 returns 16 of 66. Each result arrives as fast as the honest one. Now look at JFK at version 33, or anything on the vendor branch: the break changes nothing, because those queries already read every file. Lying statistics can only hurt where skipping is doing work, which is exactly where you are relying on it.

In a real Delta table the stats are written into the same add action as the file, in the same atomic commit, so they cannot drift apart this way. They can be missing, and then the file is simply read, or wide rather than tight, which is still safe to skip on. The break button is a demonstration of why that guarantee matters, not a common failure.

Real world

A 500 TB table that reads 7 percent. The Delta Lake paper describes an information security team that queries network flow data by source address, destination address and time, looking for one address among millions. Indexes over multi-petabyte data were too expensive, so they Z-ordered the files on several fields and let min/max skipping do the work. On a 500 TB traffic table, the authors report, those queries skipped 93 percent of the data. The figure is the vendor's own, from a customer case; the mechanism is the one in front of you.

Check yourself

Three questions

Clear all three and analyst session 8 gets stamped in your passport.

1 · At version 31 the table has 31 live files, the same as at version 30, although the MERGE inserted 31 late trips. What happened in the log?

Parquet files are never edited. A MERGE writes new files and records them with add, records the files they replace with remove, and the change data feed gets its own cdc action. The live count can stay flat while the table changes.

2 · Z-ordering by vendor_id rewrote all eight files. Why did the JFK query not improve, and why did the 15 January query get worse?

Skipping can only use the column in the filter. Clustering on a column nobody filters makes no file narrower for the questions people ask, and any rewrite can destroy an order that was already helping.

3 · With the stats shuffled, JFK at version 34 by zone reads 2 files and returns 0 of 358. JFK at version 33 still returns 358 of 358. What explains the difference?

The shuffle is fixed (the same seed in Python and the browser). A query that reads every file cannot be misled by statistics; one that relies on them to skip can. That is why stats are written in the same atomic commit as their file.
