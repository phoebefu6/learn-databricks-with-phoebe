Part 1 · covers securables and privileges

What you grant, on what

5 min live

Unity Catalog names every governed object with three parts, catalog.schema.table, and calls each of them a securable. A privilege is always granted on exactly one securable to one principal, ideally a group. Which privileges make sense depends on the level: the doors sit on the catalog and the schema, the data rights sit on the table, and models and volumes have privileges of their own.

LiveThe privileges you will actually type2 min▶

The Databricks reference "Unity Catalog privileges and securable objects" lists many privilege types; a working analyst meets a short list. USE CATALOG and USE SCHEMA are doors: they let you into a catalog or schema and give no data on their own. SELECT reads a table or view, MODIFY changes its rows. CREATE TABLE and CREATE MODEL on a schema let you add objects inside it. EXECUTE lets you load a registered model, and READ VOLUME and WRITE VOLUME govern the files in a volume.

Two more deserve a warning label. MANAGE lets a principal manage privileges, transfer ownership, rename and drop an object without owning it (Part 3). ALL PRIVILEGES sounds like everything and is not: the reference excludes EXTERNAL USE SCHEMA, EXTERNAL USE LOCATION, MANAGE and READ METADATA from it. Someone holding ALL PRIVILEGES can read and change far more data than most roles need, and still cannot manage grants.

LiveGRANT, with the securable keyword2 min▶

Every grant names the privilege, the kind of securable, its full name and the principal. The securable keyword (CATALOG, SCHEMA, TABLE) is not decoration: it tells the reader of the statement which level of the tree the grant attaches to, and therefore how far down it reaches. Principals go in backticks because group names can contain hyphens or spaces.

GRANT SELECT ON TABLE main.taxi.trips TO `analysts` attaches SELECT to one table. GRANT SELECT ON SCHEMA main.taxi TO `finance` attaches it to the schema, so it reaches every table in main.taxi. Read the keyword first, then the name; it is the fastest way to spot a grant that is wider than it looks.

Self-studyRoles, row filters and masks live next door1 min▶

Real world

"Give her everything, she is senior" (constructed). A team lead asks for a new analytics engineer to be able to "manage the taxi data". The platform engineer grants ALL PRIVILEGES on the catalog, reasoning that it must cover managing. A week later the engineer tries to grant SELECT to a new hire and cannot: ALL PRIVILEGES excludes MANAGE. Meanwhile she can change rows in every table in the catalog, which nobody asked for. The fix is two narrower grants: the read keys on the schemas she works in, and MANAGE on the one schema she was meant to look after.

Part 2 · covers how a read is decided

Three checks, in order

6 min live

When a principal reads a table, the documented rule asks three questions: may they use the catalog, may they use the schema, and do they hold SELECT on the table? Each question is answered by looking at the object itself and at every parent above it, because privileges on a catalog or schema flow down. LiveThe documented rule, and the word "future"2 min▶

The privileges reference states the read rule plainly: to read a table you need SELECT on the table, USE CATALOG on its parent catalog and USE SCHEMA on its parent schema. Rows 1 and 2 are why the rule needs memorising. With nothing granted, all three are missing. With SELECT on the table alone, the analysts group is still turned away, now for the two doors only. The classic "I was granted SELECT and still cannot see it" ticket is row 2.

The same reference says privileges granted on a catalog or schema apply to "all current and future objects" inside it. That one phrase is what makes schema-level grants cheap to run and risky to give: the grant was decided against the tables you could see that day, and it will answer for tables nobody has thought of yet.

LiveOutputs 4 and 5: one new table, two groups2 min▶

The finance group gets SELECT on the schema main.taxi plus the two doors. Then the model asks about main.taxi.zones_created_next_year, a table no grant ever named. Finance: "can read", because the SELECT check walks up from the table and finds it on main.taxi. The analysts group holds both doors and SELECT on trips only, so for the same new table it prints "denied, missing SELECT". Same schema, same day, opposite answers, decided entirely by where each SELECT was attached.

Self-studyWhat the model leaves out2 min▶

b6.py encodes one rule and nothing else, and it is worth knowing where real Unity Catalog will answer differently. It has no ownership, no MANAGE, no row filters or column masks (which shape what a reader sees after the three checks pass), no workspace bindings and no external locations. It also treats a principal as a single name, so it cannot show a user inheriting a grant through group membership. Use it to learn the three checks; use SHOW GRANTS to learn your workspace.

Real world

The table that arrived already shared (constructed). A data engineer lands a new driver-ratings table in main.taxi on a Friday. On Monday a finance analyst mentions it in a meeting, and the engineer asks who gave finance access. Nobody did, on that table. Finance held SELECT on the schema, granted months earlier for the trip tables, and row 4 above is what happened. Nothing was misconfigured; the grant did exactly what the reference says. The team now asks one question before any table lands: who already reads this schema, and should they read this too?

Part 3 · covers checking grants

Trust SHOW GRANTS, not memory

4 min live

Grants change one statement at a time, by different people, for different reasons. Any list of them kept anywhere else, a spreadsheet, a wiki page, a ticket, starts going stale the moment someone runs a GRANT by hand. The catalog itself is the only record that is always current, and SHOW GRANTS is how you read it.

LiveSHOW GRANTS and REVOKE2 min▶

SHOW GRANTS ON TABLE main.taxi.trips lists the grants recorded on that securable; SHOW GRANTS ON SCHEMA main.taxi does the same one level up. Both are standard Unity Catalog SQL commands, and because inheritance flows down, a complete answer to "who can read trips?" means looking at the table, its schema and its catalog. REVOKE SELECT ON TABLE main.taxi.trips FROM `analysts` removes a grant, with the same shape as GRANT and FROM in place of TO.

Run SHOW GRANTS before you change anything and again after. The first run tells you what is really there, which is often not what the ticket assumed; the second proves the change did what you meant and nothing more.

LiveOwners, and MANAGE without ownership1 min▶

Every securable has an owner who can grant on it. If that owner is one person, every access request waits on one inbox. The privileges reference describes MANAGE as the privilege that lets a principal manage privileges, transfer ownership, rename and drop an object without owning it. Grant MANAGE to a stewards group and the owner stops being a bottleneck. Remember the trap from Part 1: ALL PRIVILEGES does not include MANAGE.

Self-studyModels are securables too1 min▶

A model registered in Unity Catalog has a three-part name like a table, <catalog>.<schema>.<model>, and the same tree of grants. The models documentation lists what each action needs: CREATE MODEL plus USE SCHEMA on the schema to create a model, CREATE MODEL VERSION to add versions, and EXECUTE to load it. Session 7 registers a real model locally and then shows where these grants come in on Databricks.

Real world

"I have SELECT and it still says permission denied" (constructed). An analyst is told her access to main.taxi.trips is done, and her first query fails. The platform engineer resists the urge to re-grant SELECT and walks the three checks instead, with SHOW GRANTS at each level. On the table: SELECT for her group, present. On main.taxi: no USE SCHEMA for her group. On main: no USE CATALOG either. Two GRANT statements later she can read, which is output 2 becoming output 3. The ticket took five minutes because nobody had to guess.

Build-along

Model the read rule, then write the real grants

★ 22 min · everyone builds

The script needs nothing but Python: no packages, no account, no data file. Save it as b6.py and run it with python b6.py. The outputs shown are what it printed in this build under Python 3.11. Remember what it is: a local model of the documented rule, so its answers are the rule's answers, not a workspace's.

Write the model. A grant is a tuple of principal, privilege and securable. has looks for the privilege on the securable or any parent, which is inheritance. can_read runs the three checks and collects whatever is missing. This part defines functions and prints nothing.

★ b6.py, part 1# Analyst session 6: the Unity Catalog read rule, as a local model you can run anywhere. # A MODEL of the rule in the Databricks privileges reference, not Unity Catalog itself: # to read a table you need USE CATALOG on its catalog, USE SCHEMA on its schema and SELECT on # the table; a privilege granted on a catalog or schema is inherited by everything inside it. GRANTS = set() # (principal, privilege, securable) def grant(priv, securable, who): GRANTS.add((who, priv, securable)) kind = {1: "CATALOG", 2: "SCHEMA", 3: "TABLE"}[securable.count(".") + 1] print(f"GRANT {priv} ON {kind} {securable} TO `{who}`") def has(who, priv, securable): parts = securable.split(".") # the securable itself, or any parent of it, carries the privilege (inheritance flows down) return any((who, priv, ".".join(parts[:i])) in GRANTS for i in range(1, len(parts) + 1)) def can_read(who, table): cat, sch, _ = table.split(".") missing = [p for p, s in (("USE CATALOG", cat), ("USE SCHEMA", f"{cat}.{sch}"), ("SELECT", table)) if not has(who, p, s)] return "can read" if not missing else "denied, missing " + ", ".join(missing)

Grant to the analysts group, one key at a time. Ask before any grant, after SELECT alone, and after the two doors. Watch the missing list shrink.

★ b6.py, part 2T = "main.taxi.trips" print("1.", can_read("analysts", T)) grant("SELECT", T, "analysts") print("2.", can_read("analysts", T)) grant("USE CATALOG", "main", "analysts") grant("USE SCHEMA", "main.taxi", "analysts") print("3.", can_read("analysts", T))

Check yourself

Three questions

Clear all three and analyst session 6 gets stamped in your passport.

1 · The analysts group holds SELECT on main.taxi.trips and nothing else. What happens when a member reads the table?

The read rule needs all three keys. SELECT on the table is the last lock; USE CATALOG on main and USE SCHEMA on main.taxi are the doors in front of it. That is output 2.

2 · Finance holds SELECT on the schema main.taxi plus both doors. Next year an engineer creates main.taxi.zones_created_next_year. Can finance read it?

Inheritance includes the future. The SELECT check walks up from the table and finds the grant on main.taxi, which is output 4. Convenient for reporting schemas, and the reason to decide what lands in a schema before it lands.

3 · Which question can b6.py NOT answer for you?

It is a local model of one documented rule. It knows nothing about your workspace, ownership, MANAGE, row filters, column masks, workspace bindings or external locations. For the real answer, run SHOW GRANTS at each level.
