Notebooks versus jobs

Every Databricks team starts in notebooks, and it should: a notebook is where a person asks a question and sees the answer a second later. The trouble starts on the day a useful notebook gets scheduled exactly as it is, on the cluster its author happened to have open. Tonight is about the line between interactive work and automated work: why Databricks prices them differently, what a job actually is, and the short checklist a notebook should pass before it is allowed to run at 2am without anyone watching.

Part 0

Where we start

Session 3 decided who may see which table. This session decides how work reaches those tables. A person exploring data and a pipeline that refreshes a forecast every night both run code on Databricks, but they need different things: the person needs compute that stays warm between thoughts, the pipeline needs compute that starts, finishes and disappears. Databricks names the two, prices the two, and gives the second one its own product, Lakeflow Jobs. A leader who can tell them apart catches the most common cost mistake on the platform before the bill does.

Part 1 · covers interactive and automated work

Two kinds of work, two kinds of compute

5 min live

Interactive work has a human in the loop: run a cell, read the result, think, run the next one. Automated work has no human in the loop: a trigger fires, tasks run in order, the result lands somewhere. The compute that suits one is the wrong shape for the other, and the price list says so in plain words.

LiveFour kinds of compute, in the docs' words2 min▶

The Databricks compute documentation sorts compute into four kinds: serverless compute for notebooks, serverless compute for jobs, classic compute, and SQL warehouses. Serverless compute, in the docs' phrase, runs "in the serverless compute plane, which is managed by Databricks": you do not choose or manage the machines. Classic compute is the kind your team configures, machine type and size included, and it comes in the two flavours the price list separates: all-purpose for people and jobs compute for automated runs. SQL warehouses serve SQL and dashboards, and session 5 prices them by size.

Notice that the split between people and pipelines runs through all of it. Even serverless comes in a notebook flavour and a jobs flavour. The question "interactive or automated?" is built into the product, not added by finance afterwards.

LiveThe price list names the difference2 min▶

The Azure Databricks pricing page describes all-purpose compute as for "Interactive workloads to analyze data collaboratively with notebooks" and jobs compute as for "Automated workloads to run fast and robust jobs via API or UI". The list rates, Azure Databricks Premium, East US, pay as you go, read 3 October 2026: $0.55 per DBU-hour all-purpose, $0.30 per DBU-hour jobs. All-purpose costs 1.83 times as much per DBU for the same machines. AWS and GCP list prices differ, so re-read your own cloud's page before quoting a number to anyone.

A DBU is Databricks' unit of processing, billed per second; session 5 is the full arithmetic. For tonight, one fact is enough: the same work on the same cluster size costs less as a job than as a notebook someone left attached.

Self-studyDatabricks' default answer: serverless2 min▶

The classic compute best practices page says it directly: "For most new workloads, Databricks recommends using serverless compute." Read that as the vendor's recommendation, which it is, with real reasons behind it: no cluster to size, no cluster to forget to stop. The same Azure price list shows the interactive and automated split survives the move: interactive serverless is listed at $0.95 per DBU-hour and automated serverless at $0.45. Do not set those two rates beside the classic ones and pick a winner; session 5 does the arithmetic.

If your team learns on the Free Edition, serverless is all there is: it is free, for non-commercial use, and serverless only, with no custom compute. The limits change, so re-check the Free Edition limitations page before you plan a course or a pilot around them.

Real world

The forecast notebook (constructed). An analytics manager builds a weekly demand forecast in a notebook on the team's shared all-purpose cluster. It works, people start relying on it, and she clicks "schedule" from inside the notebook so it runs every night. Nothing about the code changed. What changed is that a person-shaped resource is now doing pipeline-shaped work: billed at the all-purpose rate, sharing a cluster with whoever is exploring at 2am, and reading a date she still edits by hand on Mondays. Part 3 follows this notebook through its promotion.

Part 2 · covers Lakeflow Jobs

A job is a graph of tasks

5 min live

Lakeflow Jobs is Databricks' name for automated work. The documentation describes a job as a set of tasks coordinated as a directed acyclic graph, a DAG: each task waits for the tasks it depends on, and nothing loops back. A trigger decides when the whole graph starts.

LiveJobs, tasks and triggers2 min▶

Three words carry the whole product. A task is one unit of work: a notebook, a Python script, a pipeline, and other types the docs list. A job is a set of tasks and the dependencies between them, drawn as a DAG. A trigger starts the job, and the docs name two families: time-based (a schedule) and event-based (something happens, such as a file arriving).

The documented ceilings tell you the intended scale: a job holds up to 1,000 tasks, a workspace runs up to 2,000 concurrent task runs, and the docs cap saved jobs at 12,000. The useful reading for a leader is the opposite: a single notebook that does ingest, cleaning, scoring and refreshing in one long run is using a 1,000-task tool as a one-task tool, and when it fails you learn only that "the notebook failed".

LiveFree Edition: 5 concurrent job tasks1 min▶

The Free Edition limitations page sets a maximum of 5 concurrent job tasks per account, on serverless compute only, for non-commercial use, with no SLA. Overrun the quota and compute is shut off "for the rest of the day (and in extreme cases, the rest of the month)". That is plenty to learn what a job is, build a three-task graph and watch it run. It is not a place to run a team's real pipelines. Limits change, so re-check that page before you rely on any of them.

Self-studyWhere orchestration takes over2 min▶

Retries, backfills, idempotency, how to cut a pipeline into tasks and how to design dependencies are orchestration questions, and they are the same on Databricks as anywhere else. They live in the data orchestration course; the pipelines that tasks run belong to the data engineering course. This session stays with what Databricks names and what Databricks charges for: jobs, tasks, triggers, and the compute they run on.

Real world

One notebook, four tasks (constructed). The forecast notebook from Part 1 does four things top to bottom: pull last week's orders, build features, score the model, refresh the planning dashboard. As one notebook, a failure at 3am reads "notebook failed" and someone reruns all of it, including the slow pull. Split into four tasks in one job, the failure reads "score model failed", the orders pull does not run again, and the dashboard task waits instead of showing a half-updated forecast. Same code, cut along its natural seams.

Part 3 · covers what changes when code becomes a job

From a person's notebook to a 2am run

5 min live

A notebook quietly assumes its author is present: she edits the date, she knows where the file went, she sees the error. A job cannot assume anyone is present. Everything the author used to supply by being there has to be written down before the work is automated.

LiveParameters, an owner, an identity, a governed output2 min▶

Parameters instead of edited cells. A date someone types into a cell every Monday is a manual step disguised as code. As a job parameter it is set for each run, so last Tuesday can be rerun without anyone touching the notebook, and the run record shows which value was used.

An owner and a run identity. Two different questions: who answers when it breaks, and whose permissions the code uses. A job that runs as its author stops working the day she changes team, and reads whatever she happens to be allowed to read. A job that runs as a service identity reads exactly what was granted to it, which is the grant matrix from session 3 doing its work.

Outputs to a governed table. A CSV in a personal folder is invisible to governance. A Unity Catalog table such as prod.forecasting.weekly has an owner, grants and history, so the people who rely on the forecast can find it and the people who should not see it cannot (session 3).

LiveThe same cluster, two prices2 min▶

Take one cluster of five DS3 v2 machines on Azure Databricks Premium, East US, pay as you go, read 3 October 2026. As all-purpose compute it costs $3.5275 per hour; as jobs compute, $2.59 per hour. Both include the same $1.465 an hour for the virtual machines; only the DBU part changes. A 2-hour nightly run costs $7.06 on all-purpose and $5.18 on jobs compute, which over 30 nights is $211.65 against $155.40. And if the all-purpose cluster is left on for 14 idle hours a day, those idle hours alone cost $49.39. Session 5 shows every step of this arithmetic; AWS and GCP list prices differ.

Self-studyWhen a notebook should stay a notebook2 min▶

Not everything should be promoted. Exploration, a one-off analysis for a board question, a prototype model, a data quality investigation: these are interactive by nature, and turning them into jobs adds ceremony with nothing to automate. The test is repetition without a person. If the work will run again on a cadence and someone downstream will rely on the result without watching it run, it is automated work and the checklist applies. If a person reads every result as it appears, leave it a notebook, and make sure its cluster stops when that person goes home.

Real world

The forecast notebook, promoted (constructed). The manager from Part 1 keeps her notebook for exploring. A copy becomes a four-task job: run_date is a parameter, the output goes to a forecasting table the planners already have SELECT on, the job runs as a service identity, it is owned by the analytics lead, and a failure emails the owner. It moves to jobs compute. Using the cluster prices above, a 2-hour nightly run drops from $7.06 to $5.18, and the shared cluster can now shut down at night instead of waiting for her. Your numbers will differ; the shape of the saving will not.

Build-along

The promote-a-notebook checklist

★ 22 min · everyone builds

No account and no code. You need one real notebook your team runs by hand, and the person who runs it. By the end you have a one-page checklist that notebook must pass before it is scheduled, and one rule your team agrees to.

Pick one notebook someone runs by hand every week. Ask your team which notebook would cause a phone call if it stopped. That is the candidate. Write one line about it.

★ The candidate, one lineNotebook: weekly demand forecast Run by: analytics manager, by hand, Monday mornings Relied on by: supply planners, every Monday by 10am Today it runs on: the shared all-purpose cluster

List its inputs. Every value someone types and every source it reads. Typed values become parameters; sources are written by their full three-level name, so governance can see them.

★ InputsParameters: run_date (today edited by hand in cell 2) horizon_weeks (today hard-coded as 8) Sources: prod.sales.orders prod.sales.stores Personal files read today: one CSV in a home folder -> move to a table first

Decide the trigger and the owner. Time-based or event-based. Then a named person who answers when it fails, and the identity it runs as, which should not be that person.

★ Trigger, owner, identityTrigger: time-based, weekly, Sunday 2am (event-based alternative: when the orders load finishes) Owner: analytics lead (named person, has a deputy) Runs as: a service identity with SELECT on prod.sales, write on prod.forecasting, nothing else

Decide the compute and the cost line. Jobs compute or serverless for jobs, never the all-purpose cluster. Write the expected DBUs; session 5 gives you the arithmetic, and for now a rough line is enough.

★ Compute and costCompute: jobs compute, 5 x DS3 v2 (or serverless for jobs) Expected: 3.75 DBU per hour x about 2 hours = about 7.5 DBU per run At list: $5.18 per run on jobs vs $7.06 on all-purpose (Azure Premium, East US, pay as you go, 3 Oct 2026; constructed workload, your numbers will differ)

Write the checklist. Nine boxes, four groups, each with a written answer. Copy it into your team's wiki as the template for every future promotion.

★ The promote-a-notebook checklistINPUTS [ ] Every hand-edited value is a job parameter [ ] Every source is named catalog.schema.table RUNNING [ ] Runs on jobs compute or serverless for jobs [ ] A named owner (and a deputy) [ ] Runs as a service identity, not a person [ ] Trigger written down: schedule or event OUTPUTS [ ] Writes to a governed Unity Catalog table [ ] A failure alert reaches the owner COST [ ] Expected DBUs per run, signed off (session 5)

Agree the rule. One sentence your team signs up to, so the checklist is not optional when someone is in a hurry.

★ The team ruleNothing runs on a schedule from an all-purpose cluster. Interactive work: notebooks, on compute that stops when we leave. Automated work: jobs, through this checklist, on jobs compute.
✗ The promotion that is not one"Just schedule the notebook as-is on the shared cluster, it works on my machine." (no parameters, no owner, runs as a person, all-purpose rate, output in a home folder)

The cheapest compute change is often a move, not a cut. Before anyone negotiates a discount or shrinks a cluster, list every scheduled run and check which compute it is on. Scheduled work sitting on interactive clusters pays the higher rate and keeps those clusters awake; moving it to jobs compute changes the rate without changing a line of code.

Before session 5

  2. Ask your platform owner for a list of scheduled runs and the compute each uses. Count how many run on all-purpose clusters.

Check yourself

Three questions

Clear all three and leader session 4 gets stamped in your passport.

1 · A pipeline refreshes a sales table every night with nobody watching. Which compute fits it?

Nightly and unwatched is automated work. The price list itself describes jobs compute as for "Automated workloads", at $0.30 per DBU-hour against $0.55 all-purpose (Azure Premium, East US), and it stops when the run ends.

2 · On the Free Edition, how many job tasks can run at the same time?

The Free Edition limitations page sets a maximum of 5 concurrent job tasks per account. The 1,000 and 2,000 figures are the documented Lakeflow Jobs limits per job and per workspace. Limits change: re-check the page before planning around it.

3 · What problem do job parameters fix?

A hand-edited cell is a manual step disguised as code. As a parameter the value is set for each run, can be changed to rerun a past date, and shows up in the run's record.
