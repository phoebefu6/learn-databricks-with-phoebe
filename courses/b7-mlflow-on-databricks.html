MLflow on Databricks

A model you cannot trace back to its data, its settings and its score is a guess with a file extension. MLflow is the habit that fixes that: every training attempt becomes a run that remembers what you tried, and the model you trust gets a name and an alias that the rest of the system loads by. Tonight you track two real models on a day of New York taxi trips, register the better one, point the alias @champion at it and load it by that alias, all on your laptop. Then you see the three things that change on Databricks.

Part 1 · covers tracking

A run remembers what you tried

5 min live

An experiment is a folder of attempts; a run is one attempt. Inside a run you log the parameters you chose, the metrics you got and the model itself with a signature that records its inputs and output. Tonight's experiment, taxi-tips, holds two runs trained on the same split, and the comparison you care about is one number per run.

LiveWhat a run records, and where it goes2 min▶

The Databricks MLflow documentation describes experiment tracking as logging "parameters, metrics, artifacts, and code versions". In b7.py each run logs one parameter (model), one metric (mae_usd, the mean absolute error of the predicted tip in dollars on the test set) and one artifact, the fitted model with a signature inferred from the test inputs and predictions.

On the laptop, mlflow.set_tracking_uri("sqlite:///mlflow.db") tells MLflow where to keep all of that: one sqlite file next to your script. On Databricks you skip that line. The documentation calls it Databricks-managed MLflow: the workspace is the tracking server, and a notebook's runs are recorded there without any setup.

LiveThe data behind the two numbers2 min▶

The script keeps trips picked up on 15 January 2024 with payment_type = 1 (card) and a fare above 0: 61,260 rows. The features are fare_amount, trip_distance and pu_zone (the pickup zone id); the target is tip_amount. A 75/25 train and test split with seed 15 feeds both models, so their scores are comparable.

The linear regression scores an MAE of $1.387; the random forest (100 trees, depth 8, seed 15) scores $1.331. That is real data and real error, and the gap is about six cents per trip. Whether six cents is worth a heavier model is a judgement call, and the run history is what lets you make it later with evidence. Before you lean on tips from any other payment type, read how the TLC data dictionary describes tip_amount.

Self-studyMLflow 3 is bigger than tonight1 min▶

The Databricks documentation describes MLflow 3 as covering agents and LLM applications as well as classic machine learning, including evaluation of generative output. Tonight stays with classic ML: two regressors, one metric, one registered model. Model serving, vector search and agents on Databricks are outside this track.

Real world

"Which model is in the report?" An analyst retrains a tip model four times in a week, saving each one as model_final.pkl, model_final2.pkl and so on. A month later a manager asks which one produced the numbers in a board slide, and nobody can say which features or which split it used. With one run per attempt, the answer is a run id with its parameters, metric and model attached. This team is constructed; the failure is the reason tracking exists.

Part 2 · covers the registry and aliases

Aliases, not stages

6 min live

A run holds a model; the registry gives it a name and numbered versions. Registering the forest's model creates taxi_tip_model version 1. An alias is a named pointer at one version, and code that loads models:/taxi_tip_model@champion gets whatever the alias points to today. Promoting a new model means moving the pointer; the loader never changes.

LiveModels in Unity Catalog: three-part names and aliases3 min▶

On Databricks a registered model lives in Unity Catalog under a three-part name, <catalog>.<schema>.<model>, exactly like a table. The documentation for models in Unity Catalog says mlflow.set_registry_uri("databricks-uc") is the default in MLflow 3, so in a Databricks notebook register_model lands in Unity Catalog without that line; writing it anyway makes the intent visible.

The same page is direct about the old workflow: "stages are not supported". Instead of moving a version to Staging or Production, you assign an alias such as @Champion and load with models:/cat.sch.model@Champion. Tonight's laptop registry uses the alias @champion in exactly the same way, with a one-part name because a local sqlite registry has no catalog.

LiveWho may create, add to and load a model2 min▶

Because a model sits in the same catalog and schema tree as your tables, the grants from session 6 govern it. The documentation names the privileges: CREATE MODEL plus USE SCHEMA to create a registered model, CREATE MODEL VERSION to add versions to one, and EXECUTE to load it. A scoring job therefore needs EXECUTE on the model, not ownership of it, and a team that retrains needs CREATE MODEL VERSION, not the right to create new models anywhere in the schema.

Self-studyWhere the wider MLOps story lives1 min▶

Tonight covers the Databricks side: where runs are tracked, how a model is named and how it is promoted. CI for models, monitoring drift in production and feature stores are tooling questions that span vendors; they are taught in Learn DataOps with Phoebe.

Real world

A scoring job pinned to a version number. A nightly job loads models:/tips/3. A better version 4 is registered and approved, but the job still loads version 3 until someone edits and redeploys its code, which happens two weeks later. Had the job loaded models:/tips@champion, approval would have been one call that moves the alias, and rolling back would be the same call pointed at 3. This team is constructed; the pattern is the one the Unity Catalog documentation recommends.

Part 3 · covers what MLflow refused

Two refusals worth keeping

4 min live

Building this session's script hit two errors. Both were MLflow doing its job: one refused to trust a file format it could not vouch for, the other refused an input that did not match the model's recorded contract. Both fixes are now in b7.py, and both are worth understanding before you meet them on a real project.

LiveRefusal 1: the forest was not trusted2 min▶

MLflow 3.16 saves scikit-learn models with skops, a format that lists the Python types inside a saved model and refuses to load types nobody has vouched for. The linear regression saved without complaint. The random forest did not: its trees are stored as sklearn.tree._tree.Tree objects, and MLflow refused to save the model until the script passed skops_trusted_types=["sklearn.tree._tree.Tree"].

Why so strict? MLflow's own error message explains that loading tree files from an untrusted source can crash the process or read memory out of bounds. The rule to keep: vouch only for types in a model you trained yourself, name them one by one, and never paste a trusted-types list from a model you downloaded.

LiveRefusal 2: the signature is a contract1 min▶

infer_signature(Xte, model.predict(Xte)) recorded the model's inputs as they were at logging time, with pu_zone as int32. An early version of the script predicted on a hand-built row where pu_zone was int64, and the loaded model refused it with "Can not safely convert int64 to int32". The fix was not to loosen the check; it was to predict on a real row taken from the test set, which has the logged types. A scoring job that sends the wrong types fails loudly at the door instead of quietly returning a number.

Self-studyOne JFK trip is a demo, not an evaluation1 min▶

The script ends by loading the champion by alias and predicting one real test trip from zone 132, JFK Airport: fare $85.60, 21.66 miles, predicted tip $14.93, actual tip $21.77. It proves the alias resolves and the signature accepts the input. It says nothing about how good the model is; the MAE of $1.331 on the whole test set is the evaluation, and even that is one day of card trips.

Real world

This build, not a hypothetical. Both refusals in the figure happened while the script on this page was being written with MLflow 3.16.1: the forest would not save until its tree type was vouched for, and the champion would not predict on a row whose zone id had the wrong integer width. Each fix is one line in b7.py, and each would have been the wrong line to "fix" by switching the check off.

Track, register, alias, load

Install the pinned versions. This is session 1's line plus MLflow and scikit-learn. If the January file is not already in the folder, fetch it; no account or key is needed.

★ Terminalpip install deltalake==1.6.6 duckdb==1.5.6 polars==1.44.2 pyarrow==25.0.1 pandas==3.0.6 mlflow==3.16.1 scikit-learn==1.9.1 curl -O https://d37ci6vzurychx.cloudfront.net/trip-data/yellow_tripdata_2024-01.parquet

Point MLflow at a local store and load one day of card trips. The sqlite file is your tracking server for tonight. DuckDB reads the Parquet file in place, and the split is seeded so your MAEs match.

★ b7.py, part 1import duckdb, mlflow, numpy as np from mlflow.models import infer_signature from sklearn.linear_model import LinearRegression from sklearn.ensemble import RandomForestRegressor from sklearn.metrics import mean_absolute_error from sklearn.model_selection import train_test_split mlflow.set_tracking_uri("sqlite:///mlflow.db") # Databricks: the workspace tracks for you mlflow.set_experiment("taxi-tips") df = duckdb.sql(""" SELECT fare_amount, trip_distance, PULocationID AS pu_zone, tip_amount FROM 'yellow_tripdata_2024-01.parquet' WHERE tpep_pickup_datetime >= TIMESTAMP '2024-01-15' AND tpep_pickup_datetime < TIMESTAMP '2024-01-16' AND payment_type = 1 AND fare_amount > 0 """).df() X, y = df[["fare_amount", "trip_distance", "pu_zone"]], df["tip_amount"] Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.25, random_state=15) print("card trips on 15 Jan:", len(df))
Output · laptop path, MLflow 3.16.1card trips on 15 Jan: 61260

Train two models, one run each. Every run logs a parameter, a metric and the model with its signature. The forest gets the one trusted type it needs to be saved.

★ b7.py, part 2runs = {} for name, model in [("linear", LinearRegression()), ("forest", RandomForestRegressor(n_estimators=100, max_depth=8, random_state=15))]: with mlflow.start_run(run_name=name) as run: model.fit(Xtr, ytr) mae = mean_absolute_error(yte, model.predict(Xte)) mlflow.log_param("model", name) mlflow.log_metric("mae_usd", mae) # MLflow 3 saves sklearn models with skops and refuses tree types unless you vouch for them trusted = ["sklearn.tree._tree.Tree"] if name == "forest" else None mlflow.sklearn.log_model(model, name="model", signature=infer_signature(Xte, model.predict(Xte)), skops_trusted_types=trusted) runs[name] = (run.info.run_id, mae) print(f"{name:9s} MAE ${mae:.3f}")
Output · laptop path, MLflow 3.16.1linear MAE $1.387 forest MAE $1.331

Register the winner and give it the alias. The lower MAE wins. MLflow also logs Successfully registered model 'taxi_tip_model'. and Created version '1' of model 'taxi_tip_model'. as it goes.

★ b7.py, part 3best = min(runs, key=lambda k: runs[k][1]) mv = mlflow.register_model(f"runs:/{runs[best][0]}/model", "taxi_tip_model") client = mlflow.MlflowClient() client.set_registered_model_alias("taxi_tip_model", "champion", mv.version) print("registered taxi_tip_model version", mv.version, "from", best, "as @champion")
Output · laptop path, MLflow 3.16.1registered taxi_tip_model version 1 from forest as @champion

Load by alias and predict one real trip. The loader names the alias, never a version number. The row comes from the test set, so its types match the logged signature.

★ b7.py, part 4champ = mlflow.pyfunc.load_model("models:/taxi_tip_model@champion") row = Xte[Xte["pu_zone"] == 132].head(1) # a real JFK pickup from the test set print("champion on a real JFK trip: fare $%.2f, %.2f miles, predicted tip $%.2f, actual tip $%.2f" % ( row["fare_amount"].iloc[0], row["trip_distance"].iloc[0], champ.predict(row)[0], yte[row.index[0]]))
Output · laptop path, MLflow 3.16.1champion on a real JFK trip: fare $85.60, 21.66 miles, predicted tip $14.93, actual tip $21.77

✗ Two ways to promote a model that you will regret# "promote" with a stage: Unity Catalog does not support stages client.transition_model_version_stage("taxi_tip_model", 1, "Production") # "promote" by replacing what the loader pins: delete version 1, register the new model, # and every job that loads models:/taxi_tip_model/1 breaks with no record of what it used to load client.delete_model_version("taxi_tip_model", 1)

Move the alias, never the model. Versions are history; keep them. Promotion is set_registered_model_alias(name, "champion", new_version), rollback is the same call with the old version, and every loader that asks for @champion follows without a redeploy.

1 · Unity Catalog does not support model stages. What do you use instead to mark the version production code should load?

The Unity Catalog documentation says "stages are not supported" and points to aliases. The loader names the alias; promotion moves it.

2 · Your laptop model is taxi_tip_model. What does its name look like when registered in Unity Catalog?

Models in Unity Catalog live in the same catalog and schema tree as tables, which is why the session 6 grants and the model privileges such as EXECUTE apply to them.

3 · Why did MLflow 3.16 refuse to save the random forest until the script passed skops_trusted_types?

The linear model saved fine; the forest's sklearn.tree._tree.Tree objects needed an explicit vouch. Vouch only for types in a model you trained yourself.
