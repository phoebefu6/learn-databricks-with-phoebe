Delta: a table that remembers

An ordinary folder of files forgets. Overwrite a file and yesterday is gone; delete a row and nobody can prove it was ever there. A Delta table keeps a numbered list of every change ever made to it, so it can tell an auditor what it said before the cleanup, tell an engineer who changed it, and put itself back the way it was. Tonight we open that list, read a real table's history line by line, and then decide the one thing only a leader should decide: how long the memory lasts.

Part 0

Where we start

Session 1 ended on the layer that decides which files are the table. That layer is a log: a folder called _delta_log next to the data, holding one small file per change. Everything a leader hears about Delta, audit history, time travel, rollback, "ACID", comes from reading that log in order. The numbers on this page come from a real one: the bench table the analyst track builds from 8,000 real New York taxi trips, whose every commit we can count.

Part 1 · covers the log as a numbered list of commits

Every change is a numbered commit

5 min live

Here is the bench table's whole life, read straight from its log. Thirty-one days of loads, a merge of late trips, a delete of voided fares, a compaction, a clustering experiment and a rollback. Look at the right-hand two columns: no commit ever edits a file. Each one adds whole files, removes whole files, or both.

LiveVersions are commits2 min▶

Every write to a Delta table adds one new JSON file to _delta_log, named by its version number padded to 20 digits: the bench table's delete is 00000000000000000032.json. Each line of that file is one action: add this data file, remove that one, here is who did it and why. The Delta protocol calls these files "the unit of atomicity for a table": a change is either a whole new log entry or it did not happen.

Two rules make this an audit trail rather than a diary. First, the protocol says "Writers MUST never overwrite an existing log entry", so version 32 means the same thing forever. Second, a reader asking for version N replays commits 0 to N in order: an add puts a file in the table, a remove takes it out (the file itself stays on storage as a tombstone until VACUUM, which is Part 3). The table at version N is exactly the set of files still live after commit N.

LiveHistory is an audit trail2 min▶

DESCRIBE HISTORY returns one row per commit, newest first: the version, when, the operation (WRITE, MERGE, DELETE, OPTIMIZE, RESTORE) and its parameters. The 2020 Delta Lake paper by Delta's own authors describes it as "showing where each update came from", which is the question an auditor asks.

Read it as strong evidence, not a complete one. On the bench, the OPTIMIZE ZORDER commit's parameters record only the predicate and the target file size, not which columns the files were clustered by. History tells you what kind of change happened and when; for the full detail of some operations you still need the engineer's notes or the job that ran it.

Self-studyWhat a commit costs2 min▶

Because files are never edited, a delete or an update has to write new copies of every file that holds an affected row, then remove the old ones in the same commit. This is called copy-on-write. On the bench, the 113 voided trips were spread across almost every day, so deleting them removed 30 of the 31 data files and wrote 8 new ones. The table shrank by 113 rows; the commit touched nearly all of it.

For a leader the consequence is practical: "just delete the bad rows" is a rewrite of storage, not a cheap edit, and its cost grows with how scattered the rows are. Analyst session 2 replays these log actions by hand, and analyst session 8 lets you step through every version above in the browser at the Delta log bench.

Real world

"What did the table say before the cleanup?" On the bench, 113 trips had a fare below zero, voided or refunded records, and version 32 deleted them. Imagine an auditor a week later asking whether any of those refunds belonged in last month's numbers. Without a log the honest answer is "we cannot know". With it: version 31 held 8,000 trips, version 32 holds 7,887, history names the DELETE and its predicate, and reading version 31 shows the 113 rows exactly as they were. The cleanup did not destroy the evidence; it filed it.

Part 2 · covers time travel and RESTORE

Asking the table about last Tuesday

5 min live

If a version is a list of files, then reading an old version is just reading an older list. Nothing is copied and nothing is rolled back: three readers can point at three versions of the same table at the same moment, on the same storage. RESTORE uses the same trick in the other direction.

LiveThree ways to name the past2 min▶

You will not write these, but you will see them in tickets and incident notes, and you should recognise what they mean. The Databricks docs give three forms:

  • SELECT * FROM orders VERSION AS OF 123 reads the table as it was after commit 123.
  • SELECT * FROM orders TIMESTAMP AS OF '2026-09-29' reads the latest version committed at or before that moment (the date here is only an example).
  • orders@v123 is the shorthand for the first form.

The version number is the exact one; a timestamp is the human one. In an audit, ask for both: "as reported on 30 September, which was version 412".

LiveRESTORE is a change that downstream sees2 min▶

RESTORE does not rewind the log and does not delete the commits after the target. It writes one more commit whose actions remove the current files and re-add the old ones. On the bench, restoring to version 33 wrote version 35: 8 files removed, 8 added, and the 8 added are exactly the files that version 33 had. The bad version 34 is still in history, which is what you want an auditor to see.

The governance point is in the docs: RESTORE is "a data-changing operation", recorded with dataChange true, so streaming readers of the table may process the restored rows again as if they were new, and produce duplicates. A rollback is therefore a change with consumers, not an undo button. Whoever runs it owes the downstream owners a message. How streaming consumers handle this is the subject of the streaming data course.

Self-studyThe analyst numbers behind this2 min▶

Analyst session 3 builds a smaller table from one real day of taxi trips, 15 January 2024: the morning load, the afternoon load, then a delete of the 930 trips with a negative fare. Asking for VERSION AS OF 0, 1 and 2 returns 21,617, 77,033 and 76,103 rows. RESTORE to version 1 then creates version 3, holding 77,033 rows again. Four versions, three of them distinct states, and no file was ever edited to get there.

Real world

The clustering experiment that was rolled back. On one branch of the bench, an engineer reorganised the files by vendor (version 34). It made things worse: a query for one day, 15 January, went from reading 2 of the 8 files to reading all 8. The fix was RESTORE to version 33, which wrote version 35 with the same 8 files as before, and the one-day query read 2 of 8 again. Three things a leader should notice: the bad experiment cost one command to undo, history still shows it happened, and the undo was itself a recorded change.

Part 3 · covers retention and VACUUM

History lasts as long as you decide

5 min live

A table that remembered everything forever would keep every removed file forever, and storage bills would only grow. So Delta runs two clocks, both set per table. One decides how long the history entries are kept; the other decides how long removed data files survive before VACUUM may delete them. Time travel needs both, so in practice the shorter clock wins.

LiveTwo defaults, two properties2 min▶

The Databricks docs give the defaults: delta.logRetentionDuration, how long history entries are kept, defaults to 30 days; delta.deletedFileRetentionDuration, how long removed data files are protected, defaults to 7 days. VACUUM, the command that deletes data files no longer referenced by the table, also defaults to 7 days of retention, matching the Delta protocol's own default.

Then the sentence every audit owner should know by heart, from the VACUUM page: "If you run VACUUM on a Delta table, you lose the ability to time travel back to a version older than the specified data retention period." History is not rewritten; DESCRIBE HISTORY may still list the old commit. Its files are simply gone.

LiveThe guard rails on VACUUM2 min▶

Databricks ships a safety check, spark.databricks.delta.retentionDurationCheck.enabled, that refuses risky short-retention VACUUMs unless someone deliberately turns it off. Turning it off should be a decision with a name attached, not a line in a script. VACUUM ... DRY RUN lists what would be deleted (up to 1,000 files) without deleting anything, which is the right first step before any change to retention. VACUUM also has two modes: LITE, which finds files to delete from the log, and FULL, the default.

When VACUUM runs is a scheduling question for the platform team; how schedules, retries and backfills are managed is covered in the data orchestration course. What it is allowed to delete is yours.

Self-studyWhat happens when retention is forced to zero2 min▶

Analyst session 3 does it on purpose. With the safety check off and retention set to zero, VACUUM deleted 1 file, one that no longer belonged to the latest version. Asking for version 2 afterwards failed with FileNotFoundError. The latest version still read 77,033 rows, so nothing looked wrong to anyone reading today's data. That is the danger: losing history is silent until someone needs it.

Retention is a trade between cost and recoverability. Longer file retention keeps more removed files in storage and you pay for them; shorter retention saves that storage and shortens the window in which you can answer "what did it say then?". There is no correct default, only a decision someone should own.

Real world

The month-end that could not be reproduced (constructed). A finance team reports monthly revenue from an orders table and, three weeks later, a regulator asks to see the table exactly as it was on reporting day. Meanwhile an engineer, asked to cut storage costs, had scheduled a nightly VACUUM with retention 0. History still lists the reporting-day version; time travel to it fails. Nobody broke a rule, because nobody had written one. A 30-day file retention, owned by finance and enforced by the platform team, would have cost some storage and kept the answer.

Build-along

Write the retention policy for one table

★ 22 min · everyone builds

No account and no code to run. Pick one table that matters and fill in one card. The two retention clocks become two numbers someone has signed, VACUUM and RESTORE become two named permissions, and the result is a page you can hand to an auditor and an engineer alike.

Pick the table an auditor would ask about. Not the biggest table: the one whose past numbers someone outside the data team relies on. Revenue, payments, a regulatory submission, the table behind the board pack.

★ Field 1 and 2Table: your_catalog.your_schema.orders Why history matters: month-end revenue is reported from it, and finance must be able to show the table exactly as it was on reporting day.

Decide the time-travel window in days, and justify it. Ask how long after an event someone could reasonably ask "what did it say then?". A month-end close, a quarterly review, a known audit cycle. Write the reason next to the number, because the number will be challenged by whoever pays for storage.

★ Field 3Time-travel window: 30 days. Reason: month-end figures are questioned within the following close; 30 days covers one full close plus a margin. Anything older is answered from the published report, not the table.

Set the two clocks. File retention must be at least the time-travel window, because VACUUM ends time travel at that line. Log retention can be longer, so history keeps showing what happened even after the files are gone. This is the statement an engineer would run; it is not run in this build, and the names are placeholders.

★ Fields 4 and 5, as an engineer would apply themALTER TABLE your_catalog.your_schema.orders SET TBLPROPERTIES ( 'delta.deletedFileRetentionDuration' = 'interval 30 days', 'delta.logRetentionDuration' = 'interval 90 days' )

Name who may run VACUUM and RESTORE, and who must be told. VACUUM is the only command that destroys history; RESTORE is a change downstream will see. Both deserve an owner and a notification list, the same way a production deploy does.

★ Fields 6, 7 and 8Who may VACUUM: the platform team only, on a schedule, with the retention safety check left on. A DRY RUN comes first after any retention change. Who may RESTORE: the table owner, with a second approver. Who is told: finance leads and every downstream consumer, including streaming jobs, before a RESTORE runs.

Write the history you promise, in one sentence. This is the line that goes at the top of the table's documentation, where an auditor and an engineer will both find it.

★ The promiseHistory we promise: 30 days of time travel and 90 days of audit history for your_catalog.your_schema.orders. Every change is a numbered commit, and history lasts exactly as long as we decide.
✗ The policy that deletes the evidenceVACUUM nightly with RETAIN 0 HOURS to save storage. (no window, no owner, no one told, and time travel ends every night)

Retention is a promise, so publish it. It is a promise to auditors about how far back you can answer, and to downstream readers about what a RESTORE will do to them. A promise kept in one engineer's head is not a policy. Write it down next to the table, where the people relying on it can find it.

Check yourself

Three questions

Clear all three and leader session 2 gets stamped in your passport.

1 · What is a version of a Delta table?

Files are never edited. Each commit adds and removes whole files, and reading version N means replaying commits 0 to N. On the bench, deleting 113 rows removed 30 files and added 8 in one commit.

2 · VACUUM runs with a 7-day retention. What happens to a version from 20 days ago?

VACUUM deletes files, not history. In the analyst run, time travel to the vacuumed version failed with FileNotFoundError while the latest version still read 77,033 rows: the loss is silent until someone needs the past.

3 · Why must downstream owners be told before a RESTORE?

RESTORE is a new commit that re-adds old files, recorded as a data-changing operation. The log only grows, and anything reading the table as a stream sees a change.
