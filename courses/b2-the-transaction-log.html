Part 1 · covers the four kinds of action

What one commit file holds

5 min live

A log entry is a newline-delimited JSON file: one action per line, nothing else. Your version 0 holds four lines and version 1 holds two. Read them in order and you have read the table's whole history, including the statistics that later sessions use to skip files.

LiveAction types, one per line2 min▶

PROTOCOL.md defines a log entry as a JSON file in _delta_log, named by its version zero-padded to 20 digits, holding newline-delimited actions, one per line. Your table so far uses four: commitInfo records what happened and who did it; protocol says which reader and writer features the table needs; metaData carries the schema and table settings; add brings one data file into the table. Tonight's DELETE adds a fifth, remove. You will meet cdc in session 4.

Because each line is a self-contained JSON object, reading a commit is three lines of Python: open the file, json.loads each line, look at the one key. That is the whole of the first build-along step.

LiveEvery field of an add2 min▶

The protocol lists the fields of add: path, partitionValues, size, modificationTime, dataChange, stats, tags, deletionVector, baseRowId, defaultRowCommitVersion and clusteringProvider. stats is optional, but delta-rs writes it, as a JSON string inside the JSON line, which is why the replay calls json.loads on it a second time.

The stats hold numRecords and, per column, minValues, maxValues and nullCount. Read version 1's aloud: 55,416 rows, pickups from 12:00:02 to 23:59:58, fares from -380.0 to 577.0, pickup zones 1 to 265. The protocol says these statistics "can be used for eliminating files based on query predicates", which is session 5's whole subject. Notice the -380.0 already: the voided trips you delete tonight were announced in the log before you looked at a single row.

Self-studyWhen dataChange is false1 min▶

Your WRITE and DELETE commits changed which rows the table holds. The protocol allows false for a commit that "only rearranges existing data or adds new statistics". OPTIMIZE uses it: it removes small files and adds a compacted one with the same rows, and marks the commit dataChange: false. You will see one on the bench in session 8.

Real world

Thirty-nine file actions, one file, all or nothing. On the Delta log bench built for session 8, a DELETE of 113 voided trips from a 31-file table wrote version 32 as a single JSON file holding 30 remove lines, 8 add lines and 1 cdc line. No reader ever saw 30 files removed and 8 not yet added: either the file 00000000000000000032.json exists, and all 39 file actions (plus its commitInfo) apply, or it does not, and none do.

Part 2 · covers reconciliation

Newest action per file wins

6 min live

A version is not stored anywhere as a list. It is computed: start at version 0, apply every action in ascending order, and keep what is left. The protocol calls this reconciliation. Your DELETE of trips with a fare below zero makes it visible, because for the first time a commit takes files away as well as adding one.

LiveThe replay rule, word for word3 min▶

PROTOCOL.md builds a snapshot by replaying actions in ascending version order. The latest protocol wins. The latest metaData wins. For data files, the newest action per logical file wins, where a logical file is identified by its path together with its deletion vector's unique id. If that newest action is an add, the file is present. If it is a remove, the file is a tombstone, which the protocol says exists only for the benefit of the VACUUM command.

That is exactly the replay() function in tonight's build-along: a dict keyed by path, add puts a key in, remove pops it out, versions read in sorted order. Order matters because the same path can be added in one version and removed in a later one; read them backwards and A and B would come back to life.

LiveWhy a commit is all or nothing2 min▶

The protocol says "Delta files are the unit of atomicity for a table". Writers "optimistically write out new data files" first, so file C existed on disk before version 2 did, and then commit by creating the next log entry. "Writers MUST never overwrite an existing log entry", and they create it with an atomic storage primitive. If two writers both try to create 00000000000000000002.json, only one can win; the other has to try again at a later version. That is optimistic concurrency: no lock is held while the data files are written.

Self-studyDeletion vectors, and why you saw none1 min▶

Rewriting 76,103 rows to drop 930 is honest but heavy. Deletion vectors are an optional table feature that marks deleted rows without rewriting the data file; that is why the logical file key includes the deletion vector's id. delta-rs 1.6.6 wrote no deletion vectors in this build, so the DELETE rewrote both files into one. To see which features a table on Databricks uses, read tableFeatures in DESCRIBE DETAIL.

Real world

The folder lister. An analyst skips the log and points a script at every Parquet file in trips_delta. After tonight's DELETE the folder holds three data files, A, B and C, so the script counts 21,617 + 55,416 + 76,103 = 153,136 rows for a day that has 76,103: every surviving trip twice, and the 930 voided trips back from the dead. Nothing errors. This analyst is constructed; the arithmetic is tonight's real output, and it is the reason the replay, not the folder, defines the table.

Part 3 · covers checkpoints

Shortcuts through a long log

4 min live

Replaying three JSON files is instant. Replaying years of frequent commits is not. A checkpoint is a Parquet file holding the result of the replay up to some version, and a small file called _last_checkpoint tells readers where the newest one is. With it, a reader loads one Parquet file and then replays only the JSON written after it.

LiveWhat the protocol promises about checkpoints2 min▶

A checkpoint "contains the complete replay of all actions" up to its version. Readers should prefer the newest one, and _last_checkpoint points at it. Two constraints keep it honest. For time travel, "the checkpoint used must not be newer than the time travel version": a checkpoint at version 2 cannot answer "what did version 1 hold", so the reader falls back to an older checkpoint or to the JSON. And readers "SHOULD NOT make any assumptions about the existence or frequency of checkpoints". Code that works only when a checkpoint is present is broken code that has not been caught yet.

LiveWho writes them, and how often1 min▶

The 2020 Delta Lake paper reports that "By default, our clients write checkpoints every 10 transactions"; that was the reference client the authors describe. delta-rs 1.6.6 behaved differently in this build: on the bench it wrote no checkpoint of its own in 33 commits, and the one at version 32 was made by hand. Tonight's checkpoint is the same: you call create_checkpoint() yourself. Frequency is an engine choice, which is exactly why the protocol tells readers not to count on it.

Self-studyWhat a checkpoint keeps, and what it drops1 min▶

Being the complete replay, a checkpoint holds the current protocol and metaData, every live add, and the remove tombstones that have not yet expired, because VACUUM still needs them. It never keeps commitInfo or cdc actions. So the checkpoint tells you what the table is, not how it got there: the history lives only in the JSON. Session 3 reads that history.

Real world

A million partitions, listed in 108 seconds. The 2020 Delta Lake paper reports a metadata experiment on a table with one million partitions: Delta listed it in 108 seconds, and in 17 seconds with the log cached, while Hive needed over an hour at 10,000 partitions. These are the authors' own measurements of their own system, reported in their paper. The mechanism is tonight's: reading a checkpoint and a few JSON files beats asking an object store to list a folder tree.

Write the replay and check it at every version. Your function reads only JSON. delta-rs answers the same question with file_uris() at each version, and the two sets of file names are compared.

★ b2.py, part 3def replay(path, upto=None): """Rebuild the live file set the way PROTOCOL.md says: newest action per path wins.""" live = {} for f in sorted(glob.glob(path + "/_delta_log/*.json")): v = int(os.path.basename(f).split(".")[0]) if upto is not None and v > upto: break for line in open(f): a = json.loads(line) if "add" in a: live[a["add"]["path"]] = json.loads(a["add"]["stats"]) elif "remove" in a: live.pop(a["remove"]["path"], None) return live for v in range(DeltaTable("trips_delta").version() + 1): mine = replay("trips_delta", v) theirs = {os.path.basename(u) for u in DeltaTable("trips_delta", version=v).file_uris()} rows = sum(s["numRecords"] for s in mine.values()) print(f"v{v}: my replay {len(mine)} files, {rows} rows | delta-rs agrees: {set(mine) == theirs}")
Output · laptop path, deltalake 1.6.6v0: my replay 1 files, 21617 rows | delta-rs agrees: True v1: my replay 2 files, 77033 rows | delta-rs agrees: True v2: my replay 1 files, 76103 rows | delta-rs agrees: True

The log is the only source of truth for which files count. Never list the folder and never trust one commit on its own: a commit is a change, not a state. Replay from the newest checkpoint, or from version 0, in ascending order, or let a Delta reader do it for you. The folder holds tombstoned and uncommitted files that no reader should ever count.

Check yourself

Three questions

Clear all three and analyst session 2 gets stamped in your passport.

1 · Version 2 holds remove lines for files A and B. What happens to those Parquet files when the commit lands?

A remove is a logical statement in the log, not a file operation. The bytes stay put, which is what lets you time travel to version 1, until VACUUM deletes unreferenced files after its retention period.

2 · Why must the replay read commits in ascending version order?

The protocol's rule is newest action per logical file wins. Apply v2's remove before v0's add and file A comes back to life, with 21,617 rows the table no longer holds.

3 · What is a checkpoint for?

Checkpoints only save work. Readers must not assume they exist, a checkpoint drops commitInfo and cdc, and atomicity comes from the JSON log entries, not from checkpoints.
